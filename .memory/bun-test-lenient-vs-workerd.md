Found on epic nemarOrg/nemar-cli#1181 (2026-09-02) while reviewing the zarr data-plane Worker: Bun's `Headers`/`Response` accept a non-Latin-1 code point in a header value (a decoded S3 key in a redirect `Location`), where spec-conformant workerd throws a TypeError and the request 500s via onError. Likewise `caches.default` does not exist under `bun test` (routes need a cache dependency seam), the real Cache API refuses to store a 206 (the route stores ranges as synthetic 200s), and `Vary: Origin` is ignored by the Cache API (CORS is re-applied per request on hits). None of these differences fail a Bun test.

**Why:** the backend suite is real-engine but runs on Bun, not workerd; behaviour that depends on Workers runtime semantics passes locally and breaks only in production.

**How to apply:** for any change to backend/src/routes/zarr-data.ts, data.ts or other Worker data-plane code, have the review explicitly check header byte-string validity, Cache API status rules, and per-request CORS reapplication, and encode every URL segment that reaches a client-facing header. Test doubles for the Cache API should throw on 206 to mirror the platform. See [[test-entry-point-not-callee]] and [[verify-fix-against-known-broken]].

**SQL engine, same lesson (2026-09-06, epic #1250 phase 4):** bun:sqlite does not enforce D1's LIKE/GLOB pattern-length limit, so a migration with a 79-character character-class GLOB passed the whole backend test suite and would have aborted the real deploy mid-file ("LIKE or GLOB pattern too complex: SQLITE_ERROR"). Before merging any migration, run it against real local D1 from backend/: `./node_modules/.bin/wrangler d1 execute nemar-db -c wrangler-sccn.toml --local --command "<statement>"` (no auth needed for --local), or `wrangler d1 migrations apply nemar-db -c wrangler-sccn.toml --local` on a fresh local DB. Partial unique indexes with COLLATE NOCASE do work on real D1 (verified the same day).

**Request AND response headers workerd owns (2026-09-16, nemar-cli#1419):** the git-file broker sent `Accept-Encoding: identity` to GitHub raw so upstream's `Content-Length` would mean the manifest's size. The runtime owns `Accept-Encoding`: it never reaches the origin, raw gzips anyway, and workerd strips `Content-Length` when it decodes. So the header-based size check the ADR documented had never run once in production while looking present in the code. Worse on the way out: setting `Content-Length` BY HAND on a `Response` whose body is a `ReadableStream` does not survive either, because workerd sends it chunked and drops the header. Confirmed by deploying the hand-set version (0.10.4-dev17) and re-measuring the live response. A declared length needs a body of known byte length (an ArrayBuffer/Uint8Array), so the fix buffers under a ceiling and streams with a byte counter above it. Bun's in-process harness keeps a hand-set header on a streamed body, so NO in-process test can catch this class; only a live test against the deployed worker can, which is what `test/git-broker-live.test.ts` did.
