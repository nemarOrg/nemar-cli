## Goal

The weekly import report (one issue per ISO week on `nemarDatasets/.github`, ADR 0054) carries an RFC section that lists every RFC that is open or closed awaiting a decision, with its close instant,
and says when `rfc-clock` last ran and whether GitHub still has it enabled,
so a clock that GitHub switched off after 60 days without repository activity is visible within a week (risk K1),
and an RFC section that could not be read says unknown and counts as needing attention, never as zero.

## Decided design

**Where it runs.**
Settled: inside the existing weekly report, gathered beside the other facts on the existing daily tick, behind the existing once-per-week gate.
`AGENTS.md` makes a new daily cron production-only by default; this adds no cron, so nothing about the dev cron allowlist changes.

**The data source: three GitHub reads of the public repository nemarOrg/rfcs.**
Settled:

1. `GET {GITHUB_API()}/repos/nemarOrg/rfcs/contents/README.md` with `Accept: application/vnd.github.raw`.
   The RFC list comes from the generated index between `<!-- rfc-index:start -->` and `<!-- rfc-index:end -->`, whose table columns are Number, Title, Scope, Opened (UTC), Closes (UTC), Decision and Thread (`src/index-gen.ts`).
   `rfc-check` refuses a pull request that leaves the index stale, so the index is the record; R3 does not parse `text/` files and does not copy `rfcStatus`.
   The text "No RFC has been proposed yet." between the markers is a true empty list.
2. `GET {GITHUB_API()}/repos/nemarOrg/rfcs/actions/workflows/rfc-clock.yml`: its `state` (`active`, or `disabled_inactivity`, `disabled_manually` and the like).
3. `GET {GITHUB_API()}/repos/nemarOrg/rfcs/actions/workflows/rfc-clock.yml/runs?per_page=1`: the newest run's `created_at`, `conclusion` and `html_url`.

Each read sends a named `User-Agent` and a GitHub token that `gatherRfcs` obtains itself, through `deps.token ?? getDatasetsToken` (the App installation token):
the run holds no token while facts are gathered, because `runWeeklyImportSummary` obtains one only in its post phase, after `gatherRepulls`.
If obtaining the token fails, the reads go out without it; when a read with the token answers 401, 403 or 404, it is retried once without the token, because the repository is public.
`GITHUB_API()` is called at request time, so a test's `NEMAR_GITHUB_API_URL` reaches it.

**What the section says.**
Settled: a row is listed when its Decision cell is `pending` (opened, not decided).
With the report's `now`, a row whose close instant is in the future is `open, closes CLOSE`; one whose close has passed is `closed CLOSE, decision due by DUE`, where `DUE` is the close plus 14 days (PROCESS.md: the decision is due within 14 days of the close).
Drafts, and RFCs decided or withdrawn, are not listed; their count is given in one line.
The clock line gives the workflow state, the newest run's time, its conclusion and its link.
RFC numbers and titles may appear: the RFCs are public records in a public repository.
Every count renders through `count` (ADR 0054: `null` is unknown, never zero).

**Attention.**
Settled, added to `weeklyAttention` in `shared/contract/weekly-attention.ts` as an optional `rfcs` fact, the way `repulls` is:
the section could not be read (unknown);
the workflow `state` is not `active`;
the newest run is older than 48 hours, or there is no run;
the newest run's conclusion is `failure` (the clock fails when GitHub disagrees with the record);
an RFC whose decision is due has passed `DUE` with Decision still `pending`.
A quiet week with no RFC open, an active workflow and a recent successful run needs no attention.

**Failure.**
Settled: each of the three reads is in its own try; a failed read leaves its part `null` and appends to `errors` with stage `rfcs`; a README without both markers, or a table the parser cannot read, is a failed read, never an empty list.

The implementer may choose: the exact wording of the section and the CLI line, the types' names, and how the parsing is split into pure functions.
