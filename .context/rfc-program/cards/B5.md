## Decided design

**Where things land.**
Settled: this PR's base is `draft/3.0.0`; nothing it adds goes to `main` before RFC-0001 is accepted.
The version 1 vector belongs to the version 3 suite, because the draft requires a version 3 reader to refuse a store with no `format_version`; the version 2 vectors from `2.0.1` get version 3 outcomes, because the draft requires a version 3 reader to read them with defaults.

**Schemas.**
Settled: JSON Schema draft 2020-12, as in B5a; one file per attribute document of version 3, named for it:
`root`, `uniform-group`, `level0-array`, `view-array`, `events-group`, `timestamped-group`, `time-array` and `values-array`,
with shared definitions (`valid_intervals`, `derivation`, the source fields of "Sample resolution", `zarr_conventions`, `missing_value`) in `schemas/v3/defs.schema.json`.
`$id` is `https://w3id.org/biosig-zarr/schemas/v3/NAME.schema.json` and matches the file's path.
A schema transcribes the text and adds nothing: a constraint the text does not state is not in a schema, and every `required`, `enum`, `const` and `pattern` carries a `$comment` naming the spec heading it comes from.
CONDITIONAL attributes are written with `if` and `then`.
Unknown attributes are allowed (no `additionalProperties: false` on attribute documents), because the text says a reader MUST ignore attributes it does not recognize; the `zarr_conventions` entry is the exception, closed as the text requires.
The NEMAR profile's attributes are not in the format schemas.

**The source.**
Settled: the same recording and crop as B5a (nemar `on009081` version `v1.0.0`, `sub-01/eeg/sub-01_task-rest_eeg.edf`, CC0, 100 Hz), reproduced by B5a's crop step, read only.
Record every new step and alteration in `conformance/SOURCES.md`.
Optional: if S1 has merged and lists a CC0 EDF+D file with a real gap, you MAY add one vector cut from it with Range reads; the suite does not depend on it.

**How the vectors are made.**
Settled: no writer of version 3 exists, so version 3 vectors are built by `tools/vectors/` from the crop with stock zarr-python and NumPy:
it writes the metadata documents the text specifies and the arrays with the codec chains the text names, and every resampling, quantization or alteration it applies is recorded in the store's `derivation` lists and in `SOURCES.md`.
It stays a one-purpose vector builder, not a library: it exports nothing, and nothing outside `tools/` imports it.
`v1-no-format-version` is B5a's `v2-legacy-name` with `format_version` removed and `recording_metadata` turned into a JSON string.
Invalid vectors are valid vectors altered in one controlled, recorded way, so each failure is attributable to one rule.
Keep every vector small; the whole of `conformance/`, B5a's part included, stays under 20 megabytes (MB).

**The minimum set**, by `id` (the implementer may add a vector, never drop one), with outcomes for a reader of the version 3 text:

| `id` | What it is | Expected outcome for a version 3 reader |
| --- | --- | --- |
| `v2-legacy-name`, `v2-new-name` (from B5a) | version 2 stores | accepted, read with the defaults of "Reading earlier versions" (one interval, `start_time` 0, `missing_value` null, `onset_source_basis` `unknown`) |
| `v2-version-3`, `v2-unknown-format`, `v2-no-channel-groups` (from B5a) | altered version 2 stores | `v2-version-3` is read as a version 3 store, which it is not: refused at layer 2 per `expect["3"]`; top-level `layer` null; the other two as in B5a |
| `v1-no-format-version` | no `format_version`, `recording_metadata` as a JSON string | refused as unsupported (layer 1) |

| `v3-gap-10hz` | 10 Hz, `n_samples` 40, intervals `[0, 20)` and `[24, 40)` with `source_time` 0.0 and 2.4; one sample missing inside an interval; events at 2.02 s, 0.25 s, 1.25 s and 3.25 s; view levels with factors 4 and 16 | 2.02 s has no sample (`i = 20`, in the gap); 0.25 s, 1.25 s and 3.25 s give samples 3, 13 and 33 by `floor(x + 0.5)` (a round-half-to-even reader gives 2, 12 and 32); view column 5 of factor 4 is empty by the mask rule and holds the missing value, and column 1 of factor 16 is not empty; a reader without `valid_intervals` refuses, naming it (layer 4) |

The 10 Hz rate comes from the 100 Hz source by resampling, recorded in each channel's `derivation`.
Check every tie in 64-bit floating point before relying on it (for example `0.25 * 10` is exactly `2.5`); a value that is not an exact tie is no tie case.
Every number in the table that a reader computes (samples, empty columns) is computed again by `tools/check-vectors.ts` from the vector's own metadata, and the test fails if the manifest and the computation disagree.

**Which uses of `round` the tie vectors cover.**
Settled: the onset ties of `v3-gap-10hz` alone keep the text's promise of "vectors for the `round` ties", and no quantization tie vector is made.
The text uses `round` in four places, and only the onset rule ("From an onset to a sample") is a computation a reader makes on its own to return a result.
Quantization (the formula under "Dequantization") is informative guidance that another writer MAY replace;
the start of an interval ("Valid intervals") and the stored-to-source sample mapping ("Missing values") are writer obligations whose results are stored in the store, and a reader reads them rather than recomputing them.
`conformance/README.md` says this in one sentence, so a reader of the suite sees why.

**The manifest.**
Settled: B5a's shape, unchanged: a JSON object whose top-level member `vectors` is an array; each element has `id`, `path`, `format_version`, `class`, `layer`, `rule`, `expect` and `files`.
One rule for `layer`, the same in B5a: `layer` is the reader-safety layer (1 to 4) the vector tests under the text of its own `format_version`, the same text its `class` and `rule` are judged against, or null; every version 2 entry is null, since the version 2 text has no layers; what a reader of any version does, including the layer it refuses at, is recorded only in `expect[N].refusal`.
A manifest entry's `format_version` is the major version of the text the vector was made for, not the value its store claims (the definition in `conformance/README.md` on `main`): `v3-version-4` is made for the version 3 text and tests a version 3 reader's refusal of a newer version ("Format version", layer 1), so its `format_version` is 3 and its `layer` is 1.
`expect` is keyed by the reader's format version; this card adds key `"3"` to every entry, including the capability-conditioned refusals of layer 4 and the event-to-sample results.

**The checks.**
Settled:
`tools/check-schemas.ts` also covers `schemas/v3/` and the new vectors, as B5a's rules say.
`tools/check-vectors.ts` reads only metadata and decodes no chunk; it applies the four reader-safety layers, the version rules, the onset rule and the mask rule, and compares each result with the manifest's key `"3"`.
`tools/check-vectors.test.ts` (Bun test, no mocks) proves each check can fail, and its layer 2 test relies on `v3-no-kind`: it runs the checker with one check turned off through a parameter of the checker, and asserts that at least one vector's outcome then changes.
Its tests are named exactly `layer 1: turned off, an outcome changes`, the same for `layer 2`, `layer 3` and `layer 4`, then `round ties: turned off, an outcome changes` and `mask rule: turned off, an outcome changes`.
`tools/vectors/test_vectors.py` also opens every valid version 3 vector with stock zarr-python and no other code, dequantizes with the text's formula, and compares the values with `goldens/`, missing samples as missing.

The implementer may choose: the layout of the new code inside `tools/`, the wording of the README lines, and any vector added beyond the minimum set.
