## Goal

`AMICANative(start="pamica", seed=s)` runs the Fortran binary from exactly the starting state pAMICA's array backends draw for seed `s` (the binary's first-iteration log-likelihood equals PyTorch's within 1e-12), `threads=n` makes the binary run `n` threads, and every native fit exposes the binary's SHA-256 and the settings it ran.

## Context

- Read `pamica/native/engine.py` (all), `pamica/native/resolver.py`, `pamica/tests/native_oracle.py` (all: `SeedState`, `seed_from_torch`, `reference_mixing`, `_write_f64`, `run_seeded_reference`, the facts in its docstring), `pamica/torch_impl/core.py` (`_initialize_parameters` near line 1200 and the preprocessing `fit` runs before it), `pamica/initialization.py`, `docs/api/native-backend.md`, issue #358.
- Facts: `threads` only sets `OMP_NUM_THREADS` (`engine.py:247-251`), while the binary calls `omp_set_num_threads(max_threads)` (`amica15.f90:93-100`), 10 by default, so `threads=1` runs 10 threads today; multi-threaded binary runs are not bit-reproducible run to run (`test_iteration_order_native_oracle.py` docstring).
  The binary's `load_sphere` crashes, so it computes its own sphere from the data, the same symmetric whitening pAMICA computes; seeded runs are full rank only (`native_oracle.py:214-215`).
  The documented first-iteration agreement from pAMICA's seeded state is 9e-16 (`docs/guides/validation.md`).
- No binary runs on this machine: the binary-gated tests below run in the parity workflow from PA-01 (`AMICA_RUN_FORTRAN=1`, `PAMICA_NATIVE_BINARY` set to the built shim and to the v0.4.0 release asset).

## Decided design

Settled:
1. Move `SeedState`, `seed_from_torch`, `reference_mixing`, the float64 column-major writer and the `load_*` file-and-parameter logic of `run_seeded_reference` into `pamica/native/seeding.py` (a function `write_seed_files(state, indir) -> dict` returning the `load_*` and `indir` parameters to write). `native_oracle.py` keeps its public names by importing them; its tests must pass unchanged.
2. `AMICANative.__init__(..., start: Optional[str] = None)`. `None`: unchanged (the binary draws its own start, from its `seed` parameter when given, else from the clock). `"pamica"`: `fit` builds an `AMICATorchNG` with the run's `n_models`, `n_mix`, `seed`, `rho0`, `pdftype`, `do_mean` and `do_sphere` on the CPU in float64, runs exactly the preprocessing and `_initialize_parameters` that its own `fit` runs before the first iteration (no iteration), takes `seed_from_torch`, writes the files into the run's temporary directory and sets `load_A`, `load_mean`, `load_mu`, `load_beta`, `load_rho`, `load_alpha`, `load_gm`, `load_c` to 1, `load_sphere` 0, `fix_init` 0. Any other value raises `ValueError`.
   `"pamica"` without `seed` raises `ValueError` ("a shared start needs a seed"); with `pcakeep` below the channel count, or rank-deficient data, it raises `ValueError` naming the full-rank limitation (PA-06 files the issue).
3. `threads=n` writes `max_threads n` (and keeps `OMP_NUM_THREADS`); passing both `threads` and a different `max_threads` raises `ValueError`. The default `block_size` derivation uses the resulting `max_threads`. With `threads=None` nothing changes (10 threads). The docstring says only one thread is bit-reproducible run to run.
4. After `fit`: `binary_sha256_` (hex digest of the file that ran), `binary_name_` (its basename only), `params_` (the `input.param` keys and values written, without `files`, `outdir` and `indir`), `start_`.
5. Tests in `pamica/tests/test_native_shared_start.py`:
   (a) always run: for seeds 42 and 5489, the files `write_seed_files` writes decode (column-major float64) back to the torch initial state, bit for bit, through `reference_mixing`; the `ValueError` cases of items 2 and 3; `threads=1` yields `max_threads 1` in `_input_params`;
   (b) `AMICA_RUN_FORTRAN`-gated: with the bundled `input.param` settings, `max_iter=1`, `threads=1`, `start="pamica"`, the binary's first LL equals `AMICATorchNG`'s first LL from the same seed within 1e-12, for seeds 42 and 5489, printing `PARITY tier=A1 backend=torch seed=<s> dll=<x>`; the binary's stdout reports one thread; two runs give byte-identical weights;
   (c) negative control, gated: the same run with `start=None` and `seed=42` gives a first-LL difference above 1e-6 (the binary's own draw is a different start).
The implementer may choose: helper names, how the engine captures stdout for the thread check.
