# Card PA-07: Owner operator step: CUDA float64 parity, CUDA determinism and CUDA out of memory

Status: ready
Tier: owner (never dispatched to an agent; agents never ssh to a workstation)
Timebox: about 1 hour of the owner's time, about 30 minutes of machine time
Needs: a Linux workstation with an NVIDIA GPU, run by the owner
Depends: PA-03, PA-04, PA-05 (merged into the integration branch)
Branch: the integration branch from the live facts (`$BASE`), read-only
Worktree: a fresh clone in a scratch directory on the GPU workstation
Plan: .context/plans/pamica-fixes/plan.md, section 5 (Tiers A1, A2, C and D1 for CUDA), risk K7
Review: the manager compares the pasted lines with the thresholds below and records them

## Goal

The owner runs four commands on a GPU workstation and pastes their output, which shows whether CUDA float64 meets Tiers A1, A2 and C against the v0.4.0 Linux binary from the same seed, whether two CUDA runs are bit-identical, and whether a real CUDA out-of-memory error leaves `fit` unchanged.

## Context

- No agent can run this: no CI runner has a GPU, and agents never ssh to a workstation.
- The binary is pAMICA's v0.4.0 `amica15-linux-x64` release asset, downloaded by pAMICA's own resolver, which checks it against the release's SHA-256 (`ada316d3cd8819a5e506b51b48eb464eccba133b81d4efbf63f977e680bb6b1a`); it needs glibc 2.38 or newer.
- Thresholds (plan section 5): A1 first-iteration LL difference at most 1e-12; A2 at 100 iterations LL difference at most 1e-5, minimum correlation at least 0.99999, Amari at most 1e-4; C at 2000 iterations minimum correlation at least 0.999, median at least 0.9999, Amari at most 1e-3, LL difference at most 1e-5; D1 bit-identical across two processes (reported either way: a CUDA miss is a documentation change, risk K7).

## Scope

- Commands on the owner's GPU workstation, in a scratch clone; nothing is pushed.

## Decided design

Settled: the owner runs, in a scratch directory on the GPU workstation, with `BASE` set to the integration branch name the manager gives:

```bash
git clone --depth 1 --branch "$BASE" https://github.com/sccn/pAMICA pamica-pa07 && cd pamica-pa07
uv sync --frozen
export PAMICA_NATIVE_BINARY="$(uv run python -c "from pamica.native import resolver; print(resolver.resolve('v0.4.0'))")"
nvidia-smi --query-gpu=name,compute_cap,memory.total,driver_version --format=csv,noheader
AMICA_RUN_FORTRAN=1 uv run pytest pamica/tests/test_same_seed_parity.py -k cuda -m "slow or not slow" -s -rs -q 2>&1 | grep -E "PARITY|passed|failed|skipped|xfail"
uv run pytest pamica/tests/test_reproducible_runs.py -k cuda -s -rs -q 2>&1 | grep -E "D1|D2|passed|failed|skipped"
uv run pytest pamica/tests/test_fit_outcome.py -k cuda -rs -q 2>&1 | tail -3
```

and pastes the output (the GPU's name is fine to paste; no host name is needed).
The implementer may choose: nothing.

## Acceptance

- The pasted output holds `PARITY tier=A1`, `tier=A2` and `tier=C` lines for `backend=cuda` with values within the thresholds above, or the manager files Appendix B with the owner's numbers.
- The `D1` line for CUDA says equal or not (either is recorded; "not equal" triggers risk K7's patch note to NEMAR: stop claiming CUDA bit reproducibility).
- `test_fit_outcome.py -k cuda` passes (a real `torch.cuda.OutOfMemoryError` leaves `fit` unchanged), or its failure is recorded.

## Gates

- `uv run pytest pamica/tests/test_same_seed_parity.py -k cuda -rs -q` reports no skip for lack of CUDA (the CUDA cases ran).

## Stop conditions

- The resolver refuses the binary (checksum) or the binary does not start (glibc): paste the error; the manager records it and nothing else is tried.
- No CUDA device is visible to torch: paste `uv run python -c "import torch; print(torch.cuda.is_available(), torch.version.cuda)"`.

## Report

The owner pastes the command output in the session or answers the board question with "PA-07 output pasted"; the manager records each line with `decide`.
