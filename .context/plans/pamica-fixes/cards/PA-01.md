## Goal

A new workflow `parity.yml` runs pAMICA's Fortran-gated tests on `macos-26` and `ubuntu-latest` for every pull request, each against the binary built from the pull request's source and against the pinned v0.4.0 release asset, and it is green on the final head with the failing case of #369 resolved by the owner's choice under rule D4.

## Decided design

Settled:
1. `parity.yml`: triggers `pull_request` and `push` to `dev` and `main`, both with `paths` `pamica/**`, `native/**`, `validate_implementations.py`, `pyproject.toml`, `uv.lock`, `.github/workflows/parity.yml`; concurrency per ref with cancel-in-progress for pull requests; one job `parity` with `strategy.matrix.os: [macos-26, ubuntu-latest]`, `fail-fast: false`, `timeout-minutes: 45`.
   Steps: checkout with `fetch-depth: 0` (the byte-identity pins read older commits); `astral-sh/setup-uv@v5` with Python 3.12; `uv sync` (`uv sync --extra mlx` on macOS); build the shim exactly as `ci.yml` does for that operating system; resolve the release asset with `uv run python -c "from pamica.native import resolver; print(resolver.resolve('v0.4.0'))"` into `PAMICA_RELEASE_BINARY`; print `shasum -a 256` of both binaries; then two test steps, one per binary as `PAMICA_NATIVE_BINARY`, each `AMICA_RUN_FORTRAN=1 uv run pytest -m "not slow" -n auto --no-cov -rs -s` on the nine files above, with the other binary exported as `PAMICA_REFERENCE_BINARY_B`. No step posts to an issue.
2. First push (draft PR): steps 1 and 3 only, with the test bound unchanged. This run is the measurement and the proof that the job fails on a real deviation.
3. Build floor (a measurement, always on): when `PAMICA_REFERENCE_BINARY_B` is set, every case that computes `_floor` also runs the 1-thread reference with that binary from the same seeded start, and `_floor` returns the build deviation (maximum over the trajectory, LL and `A`, as the thread floor is computed) beside the thread floor; the test prints `reference noise floor: LL <x>, A <y>` (unchanged) and `build floor: LL <x>, A <y>`.
4. Apply Q3, passed as a live fact:
   A: the bound becomes `NOISE_FACTOR * max(thread floor, build floor)` for LL and `A`, the control check uses the same maximum and must still pass, the docstring table gains the CI rows, and the ADR records the rule, its reason (section 2 item 11 of the plan) and the numbers of both legs.
   If under A torch or NumPy still exceeds the bound on any leg, do not change the bound: stop and report the lines (the manager escalates).
   B: change nothing in the bound; stop and report the measurement (an advisor consult follows).
   C: mark only the `[freeze]` case `pytest.mark.xfail(strict=True, reason="#369: ...")` naming the measured numbers, until the same-start gates of PA-03 cover it.
The implementer may choose: helper names inside the test file, the step names in the workflow.

## Acceptance

- `gh pr checks <n> -R sccn/pAMICA` is green on the final head, with both `parity` legs and every other check passing.
- `gh run view <final parity run> -R sccn/pAMICA --log | grep -E "SHA|floor|torch:|numpy:|pre-change:|passed|skipped"` shows, for each leg and binary: both SHA-256 lines, the thread floor, the build floor, the torch, NumPy and pre-change lines for the four configurations, a `passed` summary, and no skip whose reason names `AMICA_RUN_FORTRAN`.
- The control discriminates: in the same log, `pre-change` exceeds 100 times the floor the bound uses (quote the lines).
- The round-1 measurement run (bound unchanged) is quoted as red on the `[freeze]` case: the job fails on a real deviation.
- Locally, `uv run pytest pamica/tests/test_iteration_order_native_oracle.py -q` skips with the `AMICA_RUN_FORTRAN` reason.
- `uv run --with pyyaml python -c "import yaml; yaml.safe_load(open('.github/workflows/parity.yml'))"` exits 0.
- Each leg's wall time is under 45 minutes (from `gh run view <id> --json jobs`).

## Gates

- `uv run ruff check .`, `uv run ruff format --check .`, `uv run ty check .`, `uv run pytest -m "not slow" -n auto pamica/tests/test_iteration_order_native_oracle.py -q`.
- The leak check on every changed prose file (the ADR, `validation.md`, `changelog.md`).
- The full weekly suite: not run, would check: the weekly macOS job on `dev` after the epic merges.

## Stop conditions

- Step 4 is reached and Q3 is not in your live facts: stop and report the step-3 lines.
- Under A, torch or NumPy exceeds `10 * max(thread floor, build floor)` on any leg.
- The release asset fails its checksum or does not start on a runner (for example a glibc error): report the log lines; do not swap in another binary.
- Any other Fortran-gated test fails on a leg: report it; do not fix it here.
- A leg exceeds 45 minutes twice.

## Report

At most 25 lines: PR number and head; the run ids of the measurement run and the final run; per leg and binary the quoted floor, build floor, torch, NumPy and pre-change lines; the Q3 option applied; the ADR path; deviations; and a patch note for PA-02 and PA-03 naming the workflow's environment variables.
