## Goal

docs.nemar.org explains every identifier-screen finding kind, status, incomplete reason, read-failure class, reader note and local-run line.
For each, it says what was found, what was read, the remedy and how to reproduce it, under the anchor the code links to.
The text is generated from the copy tables, so it cannot drift from what the CLI and the mails print.

## Decided design

Settled:
- **The generator** imports the copy tables and prints Markdown, one section per table, in this order: statuses, finding kinds, incomplete reasons, read failures, notes, local run.
  - Each entry is a heading with an explicit `{#anchor}`, or the anchor syntax the site's Markdown supports; check how existing pages set ids.
  - Under each heading: the statement, "What was read: …", "Remedy: …", and one line "Reproduce: `nemar dataset screen --committed`" (for local-run entries, the local command form).
  - The output is deterministic: sorted within each section, no timestamps.
  - It writes between `<!-- generated:identifier-screen:start -->` and `<!-- generated:identifier-screen:end -->` in the target file, given by `--out <path>`, and refuses to write when the markers are missing.
- **Anchor test** (nemar-cli): every anchor in every screen copy table exists as a heading id in the docs checkout's identifier-screening page.
  It skips with a clear message when no docs checkout is present, as `docs-links` does.
- **The prose** outside the markers is left alone, except for a short introduction to the generated sections, if the page lacks one.
- **No claims beyond the code:** say what is not read (signals; history recordings without local content; NWB, FIF and other formats with no reader). Use the "Not read" wording from the copy table.

The implementer may choose: the heading level and the exact wording of the section introductions.
