## Goal

Measure on CI's hosted runners whether the kernel's own count of memory kills (`oom_kill` in `memory.events`) of the container's own control group, read where the launcher would read it, is 1 or more in every launch whose memory kill the engine never reported, and 0 in every exit 137 that was not a memory kill; then, only if it is, make the launcher classify a Docker 137 as `out_of_memory` (launcher exit 14) when either the engine or that count says so, with a deterministic test that fails without the change, and with the end-to-end test's expectation untouched.

## Context

- What L4 measured (run 43670682926 of draft PR 43, head 06b0a04, 300 launches per image of the memory test through the real launcher): on `ubuntu-latest` (Ubuntu 26.04.1, Docker 29.4.2, containerd 2.4.2, runc 1.5.2) the engine never reported the memory kill in 6 of 300 launches, on `ubuntu-24.04` (Docker 28.0.4) in 40 of 300.
  In those launches `State.OOMKilled` stayed `false` through 5 s of re-reads every 20 ms, the daemon emitted no `oom` event (only create, attach, start, die, destroy), and no inspect failed (first read about 16 ms after the exit, status 0).
  So the engine never learns of the kill, and no bounded re-read can repair it (L4's H2); the owner chose C (Q42): measure the kernel's own count in those launches first, then a launcher read; the end-to-end test stays strict, and each failure is rerun once meanwhile.
- How a 137 is classified today (runner epic head 240980d9): `run.run_container` returns `out_of_memory` for a 137 only when `oom_check()` is true, else `runtime_error` with detail `entry_failed` (launcher exit 13).
  `__main__.py` passes `oom_check = functools.partial(runtime.oom_killed, runtime_path, container, env)` for Docker and Podman and none for Apptainer, so under Apptainer every 137 is `out_of_memory`.
  `runtime.oom_killed` makes one `container inspect --format {{.State.OOMKilled}}` and is true only for exit 0 with the output `true`.
  Podman is refused before anything runs (`runtime.UNSUPPORTED_ENGINES`); its code paths are kept and tested with the refusal lifted.
- Where the count lives: on cgroup v2 each control group has `memory.events`, whose `oom_kill` line counts the processes of that group killed by any out-of-memory killer.
  Docker's systemd cgroup driver on cgroup v2 puts a container in `system.slice/docker-<id>.scope` under `/sys/fs/cgroup`, its cgroupfs driver in `docker/<id>`; `<id>` is the container's full 64-digit id.
  A parent's `memory.events` also counts its descendants' events unless the cgroup2 file system is mounted with `memory_localevents`.
- Who owns it: under rootful Docker the daemon creates the container's group, so the launcher can read it but never own it.
  This card's "own control group" is the container's own group, named by the id of the container the launcher named and started and holding nothing else: the nearest thing to the owner's "a control group it owns" that needs no change to the engine command line.
  A group the launcher's user truly owns exists only under the rootless engines (Apptainer, and Podman once C4 lifts its refusal), under the user's own systemd tree.
- What may be read without privilege, expected and measured in round 1: the kernel creates report-only control group files readable by every user (mode 0444) in traversable directories; the runner's user unit (`deploy/runner/nemar-runner.service`) sets no `ProtectControlGroups` and no cgroup namespace; a hosted runner's job user is not root (it has `sudo`, which the measurement never uses).
  A launcher that cannot see the host's `/sys/fs/cgroup` (inside a container of its own, or on another mount) finds no file and keeps today's answer.
- The lead's expectation, not measured: runc removes the container's group when the daemon deletes the task while handling the exit, which happens before the attached client returns, the same window in which containerd's own watcher misses the kill.
  If so, the own read finds no file and this card stops after round 1, with the during-run and parent readings as the owner's evidence for the next choice. The measurement decides, not this expectation.
- No container engine exists on the manager's machine, and workstations are out of scope, so the measurement runs where the failure happens: GitHub's hosted runners, through a temporary workflow on this card's draft PR, as L4's did.
  L4's workflow and harness exist only on closed draft PR 43 (`git fetch origin pull/43/head`, head 06b0a04): start from them.
- Collisions: C4 (to do) changes `launcher/nemar_launch/run.py` and `runtime.py` (Podman's create, inspect and start); merge order L5, then C4, and whichever merges later merges the base in and re-records `launcher_sha256` in `deploy/tapis/apps/nemar-launch.json` (`tests/deploy/test_tapis_apps.py`).
  Keep the change inside `runtime.oom_killed`, a count reader beside it and the partial in `__main__.py`, so `run.py` changes at most by a docstring sentence.

## Decided design

Settled:
1. **Round 1, the measurement.** On a draft PR into `feature/runner-epic`, the temporary workflow runs the harness on both images.
   Per image: 300 memory launches (the memory test's own argument vector from `runtime.build_argv` and its image: 128 MB, 1 CPU, the eater) and 100 control launches (the same vector and image, the entry replaced by one that holds about 96 MiB, below the limit, and then exits 137 because a child it started was killed by SIGKILL), interleaved so that every fourth launch is a control one.
   The harness runs as the job's own user and never through `sudo`. Per launch it records:
   - the client's exit status;
   - at once after the client returned, `container inspect --format '{{json .State}}'` (`OOMKilled`, `ExitCode`, the inspect's own exit status), then `container inspect --format '{{.Id}}'`, then, at the point where round 2 would read, the own group's `memory.events` (`/sys/fs/cgroup/system.slice/docker-<id>.scope/memory.events` under the systemd driver, `/sys/fs/cgroup/docker/<id>/memory.events` under cgroupfs, as the job's `docker info` names the driver): present with its `oom` and `oom_kill` values, absent, or unreadable with the error's name;
   - the parent group's `oom_kill` (the own group's parent directory, `system.slice` under the systemd driver), read before the client started and again after the own read, as a delta;
   - when the first `OOMKilled` was not `true`: re-reads every 20 ms for up to 5 s (L4's definition: a launch is lost when none says `true`) and the container's events (`docker events --since ... --until ... --filter container=<name>`), saying whether an `oom` event came;
   - during the run, with no engine call (an inspect while the container runs could change the timing being measured): a poller that finds the container's group as the new `docker-*.scope` (or cgroupfs) directory under the parent, checks once that its `cgroup.procs` is not empty, reads its `memory.events` every 20 ms, and records the largest `oom_kill` it saw and when the group vanished relative to the client's return; after the run the harness checks that the group the poller found is the one the inspect's id names (the path check).
   Once per job it prints the kernel release, `docker info --format '{{.CgroupVersion}} {{.CgroupDriver}}'`, the engine, containerd and runc versions, the cgroup2 mount options (whether `memory_localevents` is set), `id -u`, and the mode and owner of the parent group's `memory.events`.
   It ends with one line per image: `KDIAG image=<label> mem=<n> exit137=<a> lost=<b> lost_own=<absent>/<unreadable>/<zero>/<one_or_more> own_kill=<c> run_kill=<d> lost_run_kill=<e> gone_before_return=<f> parent_kill=<g> lost_parent_kill=<h> ctl=<m> ctl_exit137=<i> own_fp=<j> run_fp=<k> parent_fp=<l> path_ok=<p>/<q>`.
   Over memory launches: `lost` as above; `lost_own` splits the lost launches by their own read; `own_kill`, `run_kill` and `parent_kill` count launches whose own read, poller or parent delta saw 1 or more (`lost_run_kill` and `lost_parent_kill` among the lost); `gone_before_return` counts groups that vanished before the client returned.
   Over control launches: `ctl_exit137` those that exited 137; `own_fp`, `run_fp` and `parent_fp` those whose own read, poller or parent delta saw 1 or more (false positives). `path_ok` is path checks that agreed out of those made.
2. **Waiting for it.** The diagnostic job is this card's own measurement (about 800 launches, expected under 25 minutes), so the worker may wait for it, an exception to the preamble's rule about CI watches: `gh run view` at most once a minute, for at most 30 minutes; past that, report the run id and stop for the manager.
3. **The pre-registered reading** (the own read alone decides; the poller and the parent delta are reported for the owner, never decisive):
   `RELIABLE` when the two images together have at least one lost launch, every lost launch's own read found `oom_kill` 1 or more, no control launch's own read did (`own_fp` 0 on each image), and every path check agreed;
   `UNRELIABLE` when any lost launch's own read was absent, unreadable or 0, or any `own_fp` is above 0, or a path check disagreed;
   `NOT REPRODUCED` when neither image has a lost launch, after which the harness runs once more at 1000 memory and 250 control launches per image and is read again by these words.
4. **Round 2, the read (`RELIABLE` only).** `runtime.oom_killed` keeps its first read exactly as today, so Podman's path does not change.
   Under Docker only, when that read exited 0 and did not say `true`, it makes one more `container inspect --format {{.Id}}` (the same `CONTAINER_INSPECT_SECONDS`) and, only when the answer is exactly 64 lowercase hexadecimal digits (`re.fullmatch`), reads the kernel's count once: `memory.events` of the own group in the layout round 1 verified on CI, under the module attribute `CGROUP_ROOT` (`/sys/fs/cgroup`, which tests point elsewhere), opened without following a symbolic link, at most 4096 bytes read, holding exactly one `oom_kill` line with a non-negative decimal integer.
   It returns true when the engine said `true` or that count is 1 or more, which `run.run_container` already maps to `out_of_memory`.
   Every doubt is today's answer, false, so the 137 stays `entry_failed`: an inspect that failed or timed out, an id that is not 64 digits, no file, an unreadable or malformed file, a count of 0, and every engine but Docker.
   One read, no wait and no retry: under `RELIABLE` the count is present at that point, so a loop would add only delay; the read happens only after a 137.
   The launcher logs the outcome once, with no name, id, host or path: `oom: the engine says the container was killed for memory`, `oom: the kernel counted <k> memory kills in the container's control group`, or `oom: neither the engine nor the kernel says the container was killed for memory`.
   `__main__.py`'s partial passes the engine and the log; the command line, the name, the absence of `--rm`, the removal after the read, `codes.py` and every failure word and detail stay as they are.
5. **The deterministic tests.** An autouse fixture points `runtime.CGROUP_ROOT` at an empty temporary directory for every launcher test, so no test reads the host's own tree.
   `tests/standin/fake_docker.py`: `container inspect --format {{.Id}} <name>` prints the content of `<rec>.id`, else a fixed 64-digit default; both inspect formats are logged in `.oominspects`; any other format still exits 125; its docstring says so.
   New tests in `tests/launcher/test_runtime_docker.py`: (1) a Docker 137 the engine calls not an out-of-memory kill, whose stand-in own group holds `oom_kill 1`, is `out_of_memory`, launcher exit 14, after two inspects (it fails at the base: exit 13); (2) the same with `oom_kill 0` is `entry_failed`, exit 13; (3) no file for the id is `entry_failed`; (4) a file with no `oom_kill` line, two of them, `oom_kill x`, `oom_kill -1`, more than 4096 bytes, or a symbolic link is `entry_failed`; (5) an id that is not 64 lowercase digits (`../../x`, 63 digits, upper case) reads nothing, even when a file holding `oom_kill 1` exists where that text would point: `entry_failed`; (6) under Podman (the refusal lifted as the suite does) a 137 the engine calls not an out-of-memory kill stays `entry_failed` with no id inspect, whatever the stand-in group holds; (7) a first inspect that exits non-zero makes no id inspect and no read: `entry_failed`.
   The existing tests stay unchanged and keep passing: a 137 called an out-of-memory kill at once takes exactly one inspect; a non-137 exit takes none; a 137 the engine does not call one, with no stand-in file, is `entry_failed`.
6. **Evidence on the fixed head, then cleanup.** Before the cleanup commit the harness runs once more on both images through the fixed launcher and counts its outcomes (exit 14 against 13) over the memory and the control launches: quoted as a reading, not a gate.
   Then the temporary workflow and harness are deleted, and `git diff --stat origin/feature/runner-epic...HEAD` lists neither.
   `docs/launcher.md`, beside "An exit status of 137 is `out_of_memory` only when `OOMKilled` is true", says that under Docker the kernel's count for the container's own control group also decides, why (the engine sometimes never learns of the kill: round 1's counts per image), where and when it is read (that group, once, after the exit and before the removal), and where it is not read (item 7).
7. **The other engines and hosts.** Apptainer passes no `oom_check`, so every 137 is `out_of_memory` exactly as today; its container's group is under the user's own tree, but changing Apptainer's classification is not this card's.
   Podman keeps today's single engine read with no kernel read: rootless Podman's groups have another layout, under the user's own systemd tree, that round 1 does not measure (C4 or a later card may add it).
   A Docker daemon with another driver or a configured cgroup parent, a cgroup v1 host, and a launcher that cannot see `/sys/fs/cgroup` find no file and keep today's answer.
The implementer may choose: the harness's structure (L4's instrumented launcher run through the end-to-end rig, or a standalone script built on `runtime.build_argv`), the control entry's code, and the reader's function name, provided every launch uses the launcher's own argument vector and image and records item 1's facts.

## Stop conditions

- `UNRELIABLE`: stop after round 1 and report both `KDIAG` lines, `lost_own` per image, and what the poller and the parent delta saw in the lost launches.
  Do not change the end-to-end test's expectation: a gate's expectation changes only through the owner.
  The options for the manager to put to the owner as one question: A the end-to-end test also accepts `entry_failed` with entry exit 137 when neither the engine nor the kernel reported the kill (weakens the gate); C1 the launcher reads the parent group's count as a delta across the run, offered only if `lost_parent_kill` equals `lost` and `parent_fp` is 0 on both images: that group is shared with every container and service under it, so on a host running other workloads a 137 that was not a memory kill but coincided with another's memory kill would read `out_of_memory` (exact on CI and on a host that runs one container at a time); C2 a launcher-chosen parent group per job (`--cgroup-parent`), a change to the engine command line and to ADR 0122's flag table, which needs its own short measurement (whether such a group outlives its container long enough to be read); D keep one rerun per failure (today's practice under Q42).
- `NOT REPRODUCED` after the 1000-launch rerun: stop and report (the loop lacks something the suite has; the manager decides whether to run the suite's own order instead).
- The harness, as the job's own user, cannot read the own or the parent `memory.events` (a permission error): stop and report the modes; a read through `sudo` is not evidence.
- Round 2 would need a new failure word or detail (a nemar-cli card comes first), a change to the engine command line, the name, `--rm` or the removal's place, a new launcher input, or a change to Apptainer's or Podman's classification: stop.
