Depends: none on the board; entry condition: not before 2026-11-15T12:00-08:00 (the end of the Sunday demo) and only after the manager has recorded that the demo ended

## Goal

Measured facts, not assumptions, about pAMICA in the nemar-python image: whether the image builds with it and how long that takes, whether anything needs a compiler or GPU libraries, how the torch engine behaves on CPU in float64 (time, peak memory, determinism across thread counts), and whether pAMICA's native `amica15` release binary runs inside the image.

## Context

- Why this card changed (owner, 2026-11-14): the probe was held because the manager's machine has no Docker (16 GB of memory, arm64). The owner authorized running it on workstation B, which is native amd64, has a large scratch disk and runs Docker with its data root on that disk, after the Sunday demo ends. This replaces the lead ruling of 2026-11-13 that kept the card off every workstation, which existed only to protect the demo. The measurements are the same as before; only the host, the paths and the cleanup changed.
- Workstation B facts (DM-01 probe, public form): Ubuntu 22.04, 32 cores, 125 GiB of memory, Docker 29.8.0 (rootful, the owner's login is in the `docker` group), no `cpu` cgroup delegation to the user slice (Docker's own `--cpus` still applies, as DM-14's smoke test showed), its root filesystem is about 99 percent full, its owner-named scratch disk has about 2.7 TiB free.
- The manager gives two live facts: `$WS_DEMO` (the ssh alias of workstation B) and `$SCRATCH_B` (the owner-named scratch path on its large disk). Set `PX01_ROOT="$SCRATCH_B/px01"`.
- nemar-process base `origin/dev` holds PX-10: its Dockerfile refuses a build that does not name itself, so the build passes `NEMAR_PROCESS_VERSION` (the `-devN` version in `pyproject.toml` at the exported commit) and `NEMAR_PROCESS_COMMIT` (that commit); the build stays `dev` (the default).
- pAMICA v0.4.0's wheel does not ship `pamica/sample_data/` (its `pyproject.toml` lists only `params.json` as package data), so the sample comes from the tag.
- The demo assets stay as they are: the demo image `ghcr.io/nemarorg/nemar-python@sha256:33922cad47b58098079905edb9a06e688e533c30e0a24e364c0306f0f14c431a` stays in workstation B's Docker cache, and DM-15's runner root is never opened.
- The owner (2026-11-14): workstation B is not dedicated to this work; other people's CPU use is rare, but memory can be contested and their work comes first. So every heavy step starts only after the idle check (Decided design, item I) and runs at the lowest priority. `nice` and `ionice` on `docker build` reach only the Docker client (BuildKit runs inside the daemon), so the build is also watched and interrupted if the machine becomes busy; each fit container gets `--cpu-shares 2` beside its hard `--cpus` and `--memory` limits.

## Scope

- On the manager's machine: files only under `<operator scratch>/px01/` (a `git archive` export, the pAMICA sample and binary, the evidence).
- On workstation B: only `$PX01_ROOT` (created by this card, removed at the end) and Docker images, containers and build steps that this card creates, all tagged or named `px01`.
- Nothing on workstation B's root filesystem: no file outside `$PX01_ROOT`, `TMPDIR` set to `$PX01_ROOT/tmp` for every command. No `sudo`, no installs, no change to Docker's configuration.
- Never run `docker system prune`, `docker builder prune`, `docker image prune`, `docker volume prune`, or `docker rmi` of anything not tagged `px01:cpu`.

## Decided design

Settled, in order (save every command's output under `<operator scratch>/px01/`; on workstation B, write it under `$PX01_ROOT/out/` first and copy it back with `scp`):
I. The idle check, run before steps 0, 2, 4 and 5 and appended to `<operator scratch>/px01/idle.txt`: `ssh "$WS_DEMO" 'read l1 rest < /proc/loadavg; echo "$(date -u +%FT%TZ) load1=$l1 cpus=$(nproc) mem_avail_mb=$(( $(sed -n "s/^MemAvailable: *\([0-9]*\) kB$/\1/p" /proc/meminfo) / 1024 ))"'`. Idle only if `load1` divided by `cpus` is at most 0.9 and `mem_avail_mb` is at least 30000 (a 16 GiB build or fit plus memory left to people). If busy, wait and re-check every 15 minutes for up to 2 hours; still busy: stop (see Stop conditions).
0. Preflight on workstation B: `ssh "$WS_DEMO" "df -P / '$SCRATCH_B'; docker info --format '{{.ServerVersion}} {{.DockerRootDir}}'"`, then `ssh "$WS_DEMO" "df -P \"\$(docker info --format '{{.DockerRootDir}}')\""`. Continue only if the Docker root directory's filesystem is the scratch filesystem (same mount point) and not `/`'s, and the scratch filesystem has at least 100 GB available; record `df -P` of the scratch filesystem. Then `ssh "$WS_DEMO" "docker image inspect --format '{{json .RepoDigests}}' ghcr.io/nemarorg/nemar-python@sha256:33922cad47b58098079905edb9a06e688e533c30e0a24e364c0306f0f14c431a"` and save it as `demo-image-before.txt`.
1. Source: on the manager's machine, `git -C $NEMAR_PROCESS fetch origin`, record `C=$(git -C $NEMAR_PROCESS rev-parse origin/dev)` and `V=$(git -C $NEMAR_PROCESS show "$C:pyproject.toml" | python3 -c 'import sys, tomllib; print(tomllib.loads(sys.stdin.read())["project"]["version"])')`; then `ssh "$WS_DEMO" "mkdir -p -m 0700 '$PX01_ROOT/src' '$PX01_ROOT/tmp' '$PX01_ROOT/out' '$PX01_ROOT/in'"` and `git -C $NEMAR_PROCESS archive --format=tar "$C" | ssh "$WS_DEMO" "tar -x -C '$PX01_ROOT/src'"`. Record `uname -m` on workstation B (expected `x86_64`; every timing is labeled "native").
2. Build, at the lowest priority: `ssh "$WS_DEMO" "cd '$PX01_ROOT/src' && export TMPDIR='$PX01_ROOT/tmp' && s=\$(date +%s) && nice -n 19 ionice -c 3 docker build -f images/nemar-python/Dockerfile --build-arg NEMAR_PROCESS_VERSION=$V --build-arg NEMAR_PROCESS_COMMIT=$C -t px01:cpu . > '$PX01_ROOT/out/build.log' 2>&1; echo rc=\$? wall=\$(( \$(date +%s) - s ))s"`; while it runs, a second session repeats item I's command every 60 seconds into `<operator scratch>/px01/watch.txt`; three busy lines in a row interrupt the build (end the build command; BuildKit cancels the build) and the card goes to step 7. Record the wall seconds and `docker image inspect px01:cpu --format '{{.Size}}'`.
3. `docker run --rm px01:cpu python -c "import pamica, torch, eegprep; print(pamica.__version__, torch.__version__, torch.cuda.is_available(), eegprep.__version__)"`, and `docker run --rm px01:cpu sh -c 'command -v gcc cc gfortran nvcc || echo none'`.
4. Torch engine on EEGLAB's sample, inside the image: on the manager's machine `git clone --depth 1 --branch v0.4.0 https://github.com/sccn/pAMICA <operator scratch>/px01/pamica-src`, then `scp` its `pamica/sample_data/eeglab_data.set` and `eeglab_data.fdt` into `$PX01_ROOT/in/`. Write `<operator scratch>/px01/fit.py` (copy it to `$PX01_ROOT/in/`) that loads the set with `eegprep.pop_loadset`, takes `X = EEG["data"]` as float64, and runs `pamica.AMICA(n_models=1, n_mix=3, device="cpu").fit(X, max_iter=200, block_size=131072, seed=5489, dtype=torch.float64)` with `torch.set_num_threads(1)` inside `threadpoolctl.threadpool_limits(1)`, then again with 4 threads (both pins at 4), then again with 1 thread; for each run it prints wall seconds, `resource.getrusage(resource.RUSAGE_SELF).ru_maxrss` (kilobytes on Linux), `stop_reason_` and `final_ll_`, and at the end whether the unmixing matrices of the two 1-thread runs, and of the first 1-thread and the 4-thread run, are `numpy.array_equal`. Run it as `docker run --rm --cpus 4 --memory 16g --cpu-shares 2 -v "$PX01_ROOT/in:/in:ro" px01:cpu python /in/fit.py > "$PX01_ROOT/out/fit.out" 2>&1`.
5. Native fallback: on the manager's machine `gh release download v0.4.0 -R sccn/pAMICA -p 'amica15-linux-x64*' -D <operator scratch>/px01/amica` and check that `shasum -a 256` of the binary equals the published `.sha256` (the lead read `ada316d3cd8819a5e506b51b48eb464eccba133b81d4efbf63f977e680bb6b1a` on 2026-11-14); `scp` the binary into `$PX01_ROOT/in/amica15` with mode 0755. Then `docker run --rm -v "$PX01_ROOT/in:/in:ro" px01:cpu sh -c 'ldd /in/amica15; ldd --version | head -1'`, and run `pamica.AMICANative(binary="/in/amica15", threads=1, max_iter=200, seed=5489)` on the same sample with the step-4 limits and `--cpu-shares 2`, from a second script `native.py`, writing `$PX01_ROOT/out/native.out`; record success, wall seconds, and the Hungarian-matched minimum absolute correlation between its unmixing rows and those of a 1-thread torch run with step 4's settings that `native.py` runs itself (`scipy.optimize.linear_sum_assignment` on the absolute correlation matrix). A native run that fails (for example `libgomp.so.1 => not found`) is a finding to record, not a stop: go on to step 6.
6. CUDA flavor size, without downloading it, from the manager's machine: `curl -sIL` on the torch 2.8.0 cp312 manylinux x86_64 wheel in the `cu128` directory of the PyTorch wheel index (the index whose `cpu` directory `pyproject.toml` already names), and record `Content-Length`; no GPU run is attempted.
7. Cleanup: `scp` everything under `$PX01_ROOT/out/` to `<operator scratch>/px01/`; then `ssh "$WS_DEMO" "docker image rm px01:cpu; rm -rf '$PX01_ROOT'; test ! -e '$PX01_ROOT' && echo removed; df -P '$SCRATCH_B'"`, and repeat step 0's demo-image inspect as `demo-image-after.txt`.
The implementer may choose: the scripts' internals.

## Gates

- `diff <operator scratch>/px01/demo-image-before.txt <operator scratch>/px01/demo-image-after.txt` prints nothing (the demo image is untouched).
- `ssh "$WS_DEMO" "test ! -e '$PX01_ROOT' && ! docker image inspect px01:cpu >/dev/null 2>&1 && echo clean"` prints `clean`.

## Stop conditions

- Before 2026-11-15T12:00-08:00, or before the manager has recorded the demo's end: do not start.
- Item I still busy after 2 hours, or three busy lines in a row during the build: run step 7 and report "postponed: workstation B busy" with the idle lines (not a failure; the manager dispatches the card again later). Never start a step on a busy machine.
- Step 0 fails (Docker's root directory is on `/`, or less than 100 GB is free on the scratch filesystem), or Docker is unavailable: stop before writing anything on workstation B.
- The build fails twice: stop, report the last 30 lines of `build.log`, and still run step 7.
- A step would push, publish, need `sudo`, install anything, write outside `$PX01_ROOT`, touch the demo image or DM-15's runner root, or need a GPU: stop and run step 7.
