## Goal

Outside production, `nm099996` passes the pipeline eligibility predicate everywhere it is applied (the dispatch re-check, the eligible listing, and the claim statement's re-check) and a runner job's recipe arguments name that environment's Zarr host; in production nothing changes, byte for byte.

## Decided design

Settled:
1. `COMPUTE_FIXTURE_IDS: ReadonlySet<string> = Object.freeze(new Set(["nm099996"]))` in `compute-pipeline-eligibility.ts`, with a comment naming plan step S1 and ADR 0068.
2. One extra term clause exists only in a second, precomputed predicate: `PIPELINE_ELIGIBLE_SQL` (production) keeps its exact text; `PIPELINE_ELIGIBLE_SQL_NONPROD` replaces the `real_dataset` term's SQL with `(<the real_dataset SQL> OR (d.dataset_id IN ('nm099996') AND COALESCE(d.is_exemplar, 0) = 0))`, the list rendered from `COMPUTE_FIXTURE_IDS` with each id validated against `^nm0999\d{2}$` at module load. Every other term (active, public, not anonymous, first published, not withdrawn, not tombstoned, has a version, EEG) still applies to the fixture; `is_sandbox` is not tested for it.
3. `pipelineEligibleSql(env)` returns the non-production text only when `isNonProductionEnv(env)`; `isPipelineEligible(row, env)` and `failedPipelineTerms(row, env)` take the same decision; `loadPipelineRow(db, id, env)` passes it on. Every caller passes its own `env`; there is no default argument, so a caller that forgets fails to compile.
4. The claim statement and the dispatcher's candidate statement are built twice at module load (production and non-production) and chosen per call with `isNonProductionEnv(env)`; a test asserts the production texts are identical to the texts before this card (record them from the base commit in the test as literals).
5. `recipeZarrBase(env)` in `shared/compute-recipes.ts`: production, or `ZARR_HOSTNAME` unset or not a bare lower-case host name (`^[a-z0-9]([a-z0-9.-]*[a-z0-9])?$`), gives `RECIPE_ZARR_BASE`; outside production it gives `https://` plus `ZARR_HOSTNAME`. The runner job's `--zarr-base` argument uses it; nothing reads a host from a request, a dataset row or an index.
6. New `backend/test/compute-fixture-eligibility.test.ts` against the real D1 test database helper the existing eligibility test uses: a public, named, first-published EEG row `nm099996` with a version and `is_sandbox = 1` is eligible under `ENVIRONMENT` `development`, `staging` and `test`, refused under `production`, `""`, unset and `Production ` (with the space); the same row as an exemplar is refused everywhere; `nm099995` and `nm099900` are refused everywhere; the SQL form and the TypeScript form agree on generated rows in both environments (the existing drive-both pattern); the claim statement refuses `nm099996` under production and admits it under development through `claimRunnerJobs` with a real seeded job; `recipeZarrBase` cases including a hostile `ZARR_HOSTNAME` (`evil.example/x`, `a b`) fall back to production.
7. Every fixture id is a reserved fixture id, is not `ABSENT_DATASET_ID`, and is not in `NEVER_DEV_OWNED_IDS` (asserted in the new test).
The implementer may choose: the helper names, and whether the two statement texts live in a small map keyed by environment class.
