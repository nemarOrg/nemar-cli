## Goal

`nemar admin compute pipeline run nemar-floor-zarr --dataset <id>@<version> --executor runner` creates a `created` runner job with `accounting = 'none'`, records written, no ledger entry, and a resolved argument vector; no Tapis selection, tick or sweep can touch it; the job view shows its executor fields; every Tapis path behaves as before.

## Decided design

Settled:
- Registry: each recipe gains `input: "bids" | "zarr"` and `executors`; `nemar-floor` and `nemar-ica` are `bids`, `["tapis"]`; new `nemar-floor-zarr` 1.0.0 (a transition name, plan D12), engine `eegprep@0.5.0`, `input: "zarr"`, `executors: ["runner"]`, pool `cpu`, partition `shared` (a sizing label: `PARTITIONS.shared`'s ceiling of 64 cores and 48 hours applies), nodes 1, cores 4, memoryMb 16384 (within `QUEUE_MAX_MEMORY_MB` for `shared`; a test asserts it), gpus 0, minutes 120, `autoDispatch: false`, eligibility `eeg`.
- A `zarr` recipe resolves to `datasets: []` and the argument vector `nemar-recipe run nemar-floor-zarr --out /work/outputs/product --dataset-id <id> --dataset-version <tag> --source-commit <40 hex> --image-digest sha256:<hex> --zarr-base https://zarr.nemar.org`; `--source-commit` is the commit `resolveRun` resolves for the version (the value A6 passes for nemar-floor); the request never supplies identity.
- The run request gains `executor` (`"tapis"` default, or `"runner"`); a recipe dispatched to an executor it does not list is `invalid_body` naming `executor`; `"runner"` needs `computeRunnersEnabled(env)` (else `runners_disabled`) and sets `accounting = 'none'`.
- `createJob` for a runner job: the same validation, records and idempotency; NO hold and `estimateSuMilli` never called; new `RUNNER_JOB_INSERT_SQL` and `RUNNER_GATEWAY_USER_INSERT_SQL` gated on `RUNNER_LIVE_JOBS_GUARD_SQL` (live `executor = 'runner' AND accounting = 'none'` jobs of the pool fewer than `policy.runners.maxLiveJobs[pool]`), refusal `over_concurrency`, writing nothing; `JOB_INSERT_SQL`, `GATEWAY_USER_INSERT_SQL` and the hold statements stay byte-identical (a test pins their text); the selections below change only by the added predicate.
- Policy: optional `runners { maxLiveJobs { cpu, gpu } }`, default `{ cpu: 64, gpu: 8 }`; an absent key reads the default.
- Money and tenancy select `accounting = 'su'`: `PIPELINE_LIVE_JOBS_SQL`, the daily clamp's count, `tenantGuard`'s occupancy, the observer's settlement selection (written literally so the partial indexes still serve).
- Mechanics select `executor = 'tapis'`: `CREATED_ROWS_SQL`, `CLAIM_SUBMIT_SQL`, the cancel sweep's selection, the tenant sweep's row binding, the uncopied-terminal selection's Tapis branch, and the admin `advance` route (a runner job is refused `invalid_body` naming `executor`).
- `jobView` adds `executor`, `accounting`, `runner_backend`, `runner_id`, `runner_claimed_at`, `runner_wall_seconds`, `runner_cpu_seconds`, `runner_max_rss_mb`, and keeps `image_digest` where it is.
- CLI: `nemar admin compute pipeline run <recipe> --dataset <id>[@version] [--executor tapis|runner] [--dry-run] [--json]`; the dry run reports `executor` and the runner room.
The implementer may choose: how the runner branch is factored inside `createJob`.
