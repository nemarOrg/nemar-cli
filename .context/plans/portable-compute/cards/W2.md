## Goal

The gated page `admin/operations/workstation-runners` holds everything an administrator needs to run, register, verify, revoke and tear down a workstation runner, including the host facts that must never enter a public repository, and the etiquette that lets the runner share a lab machine with people (who may use the GPU and when, and how anyone reserves it without asking); the gated systems inventory records each runner host's role, who else uses it, and its single-tenant status as the owner confirmed it (or says it is unconfirmed).

## Context

- nemarOrg/docs is private at source and pages under `src/content/docs/admin/` are served only to administrators; this is where host names, accounts, aliases, paths and runtimes belong. Read its `AGENTS.md` (gating, `pagefind: false` as a top-level frontmatter field, the admin-gating check run by `bun run build`).
- Facts come from the manager, never guessed: `$OPS_NOTES` (a mode-0600 file in the manager's scratch with the aliases, accounts, scratch paths and which workstation runs the conversion cron) and the operator evidence of DM-01 (probe findings), DM-14 (image on the workstation), DM-15 (the recorded run's commands), DM-19 (the manual run), and S0 (teardown) if done. The public probe findings (nemar-cli PR #2147) say "workstation A" and "workstation B"; this page may name them.
- The existing page `admin/operations/systems-inventory.md` is the inventory; edit only its runner-related rows or section.
- `nemar admin docs admin/operations/workstation-runners` reads a gated page with an administrator's key.
- The owner (2026-11-14): the workstations are not dedicated to this work; the CPU is rarely used by others, memory can be contested, and the GPU is usually idle except when developers work (a deadline now). The runner takes only idle capacity and runs at the lowest priority (card L2: `availability` object, `pause` file); a GPU-optional job gets the GPU only when L3's six-sample check finds it idle and unreserved, is capped at a fraction of its memory, and moves to the CPU on an out-of-memory error or another process (card Q1c); there is no preemption of a started job in this version. Reservations are files named `gpu0`, `gpu1` and so on, or `gpu-all`, and `pause`, in the runner's reservation directories; a lab member without the runner account needs a shared directory the owner creates on the host and lists in the runner's `reservation_dirs`. `$OPS_NOTES` gives that directory, the host's other accounts and the `docker` group's members if the owner has provided them.

## Decided design

Settled, the page's sections:
1. Hosts: which workstation may run a runner (the one without the production conversion cron, owner decision Q7) and which never does without a new owner decision; the runtime found on each (DM-01), the scratch path, the runner account, and the rule that no runner card lists, opens or writes the converter's directories.
2. Registration: owner-only, the exact `admin compute runners register` command with the capacity formulas of DM-15 step 5, the site and trust words, how the secret reaches the host (piped, `umask 077`, never printed), and the key-rotation residual (a key revocation does not end a registration; revoke the registration).
3. Configuration and `doctor`: the configuration keys as built, mode 0600, the boot line, what each `doctor` line means, and when limits are enforced (Docker always; Apptainer only with `doctor`'s limits line yes).
4. Images: verify by digest and signature (the `cosign verify` command with the workflow identity), never by tag; the demo's operator-built path is labeled unsigned.
5. Running: the demo and staging commands as run (DM-15, S2S), and the user service (S4's units) marked "not yet exercised" until S2D reports.
6. Revocation and incidents: revoke a registration (`admin compute runners revoke <id>`) and what it does (claims released, started jobs `unreported`, outputs refused); K4's procedure if a non-public dataset ever reaches a runner (stop dispatch, revoke, record an incident note here).
7. Teardown: S0's steps.
8. Staging: the fixture `nm099996` and its versions, staging keys' handling (`test-admin`, `test-owner`, isolated configuration).
9. Sharing the machine (etiquette): people first: lab members' interactive and development work always has priority, and the runner takes only what is idle (L2's thresholds as built: load per CPU, the memory reserve, free scratch) at the lowest CPU and I/O priority; a started job is not preempted (to get the machine back at once, `touch` the `pause` file and ask the owner to stop the service). Who may use the GPU and when: any lab member, at any time, with no notice; NEMAR uses it only when it is idle by L3's rule (no compute process, almost no memory in use, low utilization, over six samples), takes at most the configured fraction of its memory, and falls back to the CPU rather than compete. How to reserve: `touch` a file named for the GPU (`gpu0`, or `gpu-all`) in the shared reservation directory, remove it when done (there is no expiry; the runner's `gpu-check` shows active reservations); a `pause` file stops all claims. Where the shared directory is, who created it and its mode. How to see what the runner is doing: its `availability` and `gpu-check` commands and `journalctl --user -u nemar-runner.service`. Until L3 has merged, the GPU parts say "not yet built (card L3)".
Inventory: for each runner host, a line "runner role: yes or no; container runtime; other people's accounts on the host: yes (how many) or no; members of the `docker` group besides the runner account: how many; single-tenant (ADR 0122): confirmed by the owner on a date, or not confirmed (then no production runner under Docker on this host); the owner's ON answer and its date".
The implementer may choose: the page's headings.
