## Goal

An administrator can list jobs by executor, accounting class and runner, sees in the account report which jobs were runner jobs and what they used in runner-reported core-hours (kept apart from service units), can read one report of every runner's usage over a date range, and every row whose usage the runner marked partial says so.

## Decided design

Settled:
1. Migration `014N`: `ALTER TABLE compute_jobs ADD COLUMN runner_usage_partial INTEGER CONSTRAINT compute_jobs_runner_usage_partial CHECK (runner_usage_partial IS NULL OR runner_usage_partial IN (0, 1));` (NULL for every Tapis job and for a runner job that has not completed). `RECORD_USAGE_SQL` also writes it from the completion's `usage_partial`.
2. `JobListQuery` gains `executor` (`tapis` or `runner`), `accounting` (`su` or `none`) and `runner` (a runner id matching the contract's `RUNNER_ID_RE`), each a bound column test; the route reads them from the query string and refuses anything else with the route's existing refusal; the CLI's `jobs list` gains `--executor`, `--accounting` and `--runner`.
3. `accountReport`'s per-job rows gain `executor`, `accounting`, `runner_id` and, for a runner job, `runner_usage` `{ wall_seconds, cpu_seconds, max_rss_mb, partial }`; `totals` and `by_pool` stay service units only and count only `accounting = 'su'` jobs; a separate `runner_totals` `{ jobs, wall_seconds, cpu_seconds, core_hours, partial_jobs }` holds the runner jobs, where `core_hours` is `cpu_seconds / 3600` rounded down to three decimals and labeled "runner-reported core-hours" in every human sentence.
4. New `GET /admin/compute/reports/runners?from=YYYY-MM-DD&to=YYYY-MM-DD` (administrator): per runner registration (id, name, site, trust, revoked or not), the count of jobs by state, the sums of wall and CPU seconds, the largest resident memory, and `partial_jobs`; a range is at most 366 days. CLI: `nemar admin compute runners usage --from <date> --to <date> [--json]`, whose human output ends with the line "Runner-reported usage; never service units."
5. Human output marks a partial row with ` (partial: Docker or Podman)` and never prints SU next to a runner job.
6. Tests in `backend/test/compute-runner-reporting.test.ts` against the real D1 test database with real jobs driven through the real runner routes (the pattern of `compute-runner-queue.test.ts`): a Tapis job and two runner jobs (one partial) give SU totals equal to the Tapis job alone, runner totals equal to the two runner jobs, and the partial flag where expected; the list filters; the date-range bound; and a CLI test of the new command's human and JSON output.
The implementer may choose: field order and the helper names.
