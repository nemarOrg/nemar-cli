## Decided design

Settled:
1. **Command.** `nemar-floor` declares an input option `--input` with the choices `bids` (default) and `zarr`. With `bids` every argument, rule and exit code is today's floor's. With `zarr` every argument, rule and exit code is today's `nemar-floor-zarr`'s (`--dataset-dir` refused, `--zarr-base`, `--dataset-id`, `--dataset-version`, `--source-commit` required, the attestation options, `--recording` by source or store path, the allowlist and the one-redirect rule), and `aggregate` still refuses Zarr input (exit 2).
2. **The old name.** `nemar-recipe run nemar-floor-zarr ...` exits 2 with the one standard-error line `nemar-floor-zarr is now: nemar-floor --input zarr`. `nemar-recipe version` lists `"recipes": {"nemar-floor": "1.0.0"}` and a new key `"inputs": {"nemar-floor": ["bids", "zarr"]}`.
3. **Names and version.** The product label is `nemarfloor` for both inputs, so a Zarr product's files are `desc-nemarfloor_*`; `pipelineInfo.name` is `nemar-floor` and `RECIPE_VERSION` stays `1.0.0` (BIDS records do not change by a byte; no Zarr-input record of this name existed before).
4. **What a Zarr-input record adds**, beside the `input` and `reader` blocks `nemar-floor-zarr` already writes (unchanged):
   - per store, `extensions.nemar.input.group` (the channel group read) and `extensions.nemar.input.content_sha256`;
   - in the dataset record, `extensions.nemar.input.stores_content` (the list of `{"path", "group", "content_sha256"}` for every store whose group was read in full, sorted by path), `extensions.nemar.input.input_digest` (`sha256:` and 64 hexadecimal digits), and `extensions.nemar.input.stores_unread` (the sorted list of the paths of the stores in scope that have no digest, never read or not digestable; an empty list when every store was read in full, never a count).
   BIDS-input records add nothing.
5. **The digest (`nemar.store-content.v1`, card V1 item 1)**, computed in `common/zarr_input.py` from the window `load_recording` returned: SHA-256 of the header lines `nemar.store-content.v1`, `shape C S`, `rate` plus the 16 lowercase hexadecimal digits of `window.rate` as a big-endian binary64, `unit` plus a space and `window.unit` (or `unit` alone when it is `None`), one `label` line per channel from `window.labels` (or `label` alone), `data float64-le`, each ending in a line feed, followed by `numpy.ascontiguousarray(window.data, dtype="<f8").tobytes(order="C")`, under card V1 item 1's two rules: labels all or none, the unit shared or none (an empty unit is no unit), each text hashed as its UTF-8 bytes as given, with no normalization and no trimming. `window.original_rate` is never read. A store has no digest when a unit or label that enters the header holds a carriage return, a line feed or a lone surrogate, when its rate or a value is not finite, or when it has fewer than one channel or sample: it is `failed` with the code `convert_failed` and the detail `undigestable_metadata`, and its path is in `stores_unread`.
6. **The input digest (card V1 item 2):** `sha256:` and the SHA-256 of the lines `path TAB group TAB content_sha256 LF` over `stores_content`, in code point order of the paths (Python's `sorted`), each text as given. The function raises `ValueError` for a repeated path, an empty path or group, a tab, carriage return, line feed or lone surrogate in a path or group, and a `content_sha256` that is not 64 lowercase hexadecimal digits under `re.fullmatch`. Zero rows is kept as the digest of no bytes: the TypeScript refuses it, and card V1b's check for a non-empty `stores_content` comes before any recomputation, so the difference never keys a derivative.
7. **Vectors** that `tests/recipes/test_store_content.py` asserts with the digest function on plain NumPy arrays (computed by the lead in three languages): digital `[[1, -2, 3], [32767, -32768, 0]]` (int16), scale `[0.1, 0.25]`, offset `[0.0, -12.5]` turned into physical values by eegprep-lean's `to_physical`, rate 250.0, unit "µV", labels `("Fz", "Cz")` gives `0c268ca3444e5c884afb5475ae13b6bc3170869776b2e4b0118205f2f08f84cd`; the same with unit `None` and labels `None` gives `6bff43f9934204b3bf515734cc563ef72da392cc594dc2cdcbd317d9e98f58fd`; the input digest of the one row (`sub-01/eeg/sub-01_task-rest_eeg.edf`, `eeg`, the first digest) is `sha256:bea77ea8a233ae2507f192e48548af37b8acf01c8abb0e65143ac3178e44bc0b`. Also card V1's partly labeled and code point order vectors, and its eighth, two roundings never fused: digital `[[3]]`, scale `[0.1]`, offset `[-0.3]`, rate 250.0, no unit and no labels gives `2aa312ed5d306f1f4e3331f7eff09a23972ae2b8bf8792732a79c6e156c3cb0b`, where a fused multiply-add would give `ebb90d19f4a23ee757676711f168ad69e2564e98267005d526941eb49dffc536`.
8. **Equality with the old recipe** (evidence, not a committed test): at the base commit run `nemar-recipe run nemar-floor-zarr` on the public dataset `nm000274` version `v1.0.5` with the arguments of the demo brief's F2-a command (source commit `64feed5210ebea128a8484acd3027f9551ff2d7e`, tag commit `91a8f5c9c83117b7e064cf7ae4eef1220b81cf57`, `metadata_only`, the two `.nemar/` delta paths), then the same with `nemar-floor --input zarr` at your head; every `_channels.tsv`, `_badsegments.tsv`, `_filters.json`, `_qc.json` and the recordings table are byte-identical after the label rename, and the records are equal after removing the clock, the run id, the label in names, `pipelineInfo.name` and the new fields of item 4. For BIDS input, the same comparison of a base and a head run on the repository's EEG fixture finds every file equal after removing the clock and the run id.
