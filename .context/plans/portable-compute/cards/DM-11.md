## Goal

`nemar-runner` exists with `doctor`, `once` and `run`: it exchanges its secret, claims a list of jobs, runs each through the launcher in its own scratch under Apptainer, Docker or Podman, heartbeats, enforces deadline and memory, completes with measured usage, and always deletes the job's scratch; its integration with NEMAR's real routes is DM-18's.

## Decided design

Settled:
- Configuration JSON at `$XDG_CONFIG_HOME/nemar-runner/config.json` (default `~/.config/...`): `api_base`, `secret_file`, `root`, `sif_root`, `runtime` (`apptainer`, `docker` or `podman`), `slots`, `arch`, `max_scratch_gb`, and `default_job_memory_mb` (a positive integer, REQUIRED when `runtime` is `docker` or `podman`, optional under Apptainer); refuse to start if the config or secret file is readable by group or others, if `root` is not owned by the user, or if `runtime` is `docker` or `podman` and `default_job_memory_mb` is missing.
- HTTP: `User-Agent: nemar-runner/<version>`; every request carries `protocol` where the contract says so; the access token is exchanged at start and 60 s before expiry, kept in memory, never logged.
- Claim: `run` polls every 15 s while a slot is free; `once` claims once and waits for its jobs; the answer's `jobs` list is run in parallel up to `slots`.
- Per job, under `<root>/jobs/<job id>/` (mode 0700): `out/`, `scratch/`, `home/`. Refuse to claim when free space under `root` is below `max_scratch_gb`.
- Image: Apptainer needs `<sif_root>/<hex>.sif`. Config `sif_pull` (boolean, default `false`): when false the runner never pulls, and a missing SIF completes the job with `exit_number` 13, `launcher_failure_code` `runtime_error` and `launcher_detail` the launcher's image-missing word, without launching; the operator places the SIF and verifies it (DM-14). When true (development only; the residual is a pull by the mutable tag with no digest or signature check, documented in `docs/runner.md` until outline step C2), `apptainer pull <sif_root>/.<hex>.sif.part oras://ghcr.io/nemarorg/nemar-python-sif:sha256-<hex>` then an atomic rename. A pull happens before any heartbeat: if it takes longer than the lease less 60 s, the runner abandons that job without completing it (the lease expires and the job waits again, unstarted), keeps the pulled file, and logs `claim_abandoned_during_pull job=<id>`. Docker and Podman pull by digest inside the launcher, after `started`.
- Readiness probe (`doctor`): `apptainer exec --containall --cleanenv --no-home --no-mount bind-paths --memory 64M --cpus 1 <sif> true` (the launcher's isolation flags, confirmed by the lead).
- Launch: `python3 -I -S -c '<the runpy boot line of docs/launcher.md>' <launcher dir>` in a new process group, environment built from nothing but `NEMAR_LAUNCH_SPEC`, `NEMAR_SIF_ROOT`, `NEMAR_OUTPUT_DIR`, `NEMAR_SCRATCH_DIR`, `NEMAR_JOB_END_TIME` (claim time plus the job's minutes), `NEMAR_LEASE_ID`, `NEMAR_CONTAINER_RUNTIME`, `NEMAR_ENFORCE_LIMITS` (`1` only when `doctor` proved cgroup delegation with `apptainer exec --memory 64M --cpus 1`), `NEMAR_CPUS` (always: the claimed job's `cores`, a positive integer), `NEMAR_MEMORY_MB` (under Docker or Podman ALWAYS: the claimed `memory_mb`, or, when it is null, `default_job_memory_mb`, logged as `memory_default_applied job=<id> mb=<n>`; under Apptainer only when the claimed `memory_mb` is not null), `NEMAR_RUNNER_LABEL` (under Docker or Podman only: the runner's registration id from `GET /compute/runners/me`, `rnr_` plus 24 lowercase hex), `HOME=<job>/home`, `PATH=/usr/local/bin:/usr/bin:/bin`, `LANG=C.UTF-8`.
  Lead ruling (DM-09, nemar-process PR #20): the launch specification carries no cores or memory, by design and byte-pinned, so the runner passes them from the claim answer; the launcher fails closed when `NEMAR_ENFORCE_LIMITS=1` has no usable `NEMAR_CPUS`, and (DM-10, PR #21) under Docker or Podman when `NEMAR_MEMORY_MB` is missing, because the runner's watchdog sees only the engine's client process there. `docs/runner.md` lists both keys, their source and the default. The memory watchdog uses the same value.
- Heartbeat thread: starts only after the launcher process is spawned (never before or during an image pull; no other phase exists in the contract), sends `started` at once, then every 60 s; phase `uploading` once `<job>/out/launcher/result.json` exists (confirm the path in `launcher/nemar_launch/`; use the real one and say so).
- Runner death (lead ruling, review of PR #23): on Linux the launcher child is started with `prctl(PR_SET_PDEATHSIG, SIGTERM)` through `ctypes` (the launcher forwards SIGTERM to its container); elsewhere the runner logs `pdeathsig_unavailable`. Each launcher's pid, process-group id and `/proc/<pid>/stat` start time go into `<root>/pids/<job id>.json` before the heartbeat starts; at runner start, in this order: send SIGTERM, then after 30 s SIGKILL, to every recorded group whose leader's start time still matches; remove labeled containers; only then delete leftover job directories and pid files. SIGHUP is handled exactly as SIGTERM.
  `docs/runner.md` replaces "nothing of the job outlives it" with the guarantees above and the residual: the launcher has no deadline timer of its own until outline step L1.
- Deadline and memory: SIGTERM to the process group at `NEMAR_JOB_END_TIME` plus 60 s, SIGKILL 30 s later; without enforced limits, a watchdog sums the resident memory of the process tree every 10 s and sends SIGTERM above the job's `memory_mb`.
- Cancel or `lease_lost`: SIGTERM, 30 s, SIGKILL; then complete (cancel) or stop without completing (lease lost).
- Usage: `os.wait4` gives wall, CPU (user plus system) and max resident memory; under Docker or Podman `usage_partial` is true and the log says `usage_partial runtime=<runtime>`.
- Discard: `shutil.rmtree` of the job directory in a `finally`, then `scratch_discarded job=<id> bytes=<n>`; at start, every leftover under `<root>/jobs/` is deleted and logged.
- Containers (Docker or Podman; DM-10 labels each with `nemar.job=<job id>`): after a lost lease, a cancel, a deadline kill or any launcher exit, `<engine> ps -aq --filter label=nemar.runner=<runner id> --filter label=nemar.job=<job id>` then `<engine> rm --force --volumes <ids>` when any id is listed; at runner start, the same with `--filter label=nemar.runner=<runner id> --filter label=nemar.job` (only this runner's leftovers, never another runner's on a shared daemon), each removal logged as `container_removed job=<id>`. Under Apptainer nothing is done.
- Logs: JSON lines to `<root>/runner.log` and stderr; never a secret, token, presigned address or launch value.
- `doctor` prints yes or no for: config and secret permissions, runtime and version, `sif_root` writable, egress to `api_base`, token exchange, limits; under Docker or Podman it also runs the launcher's engine preflight that DM-10 adds (call the function PR #21 names) and prints its two results as `engine limits enforceable` and `engine mode accepted` (rootless Docker without enforceable limits answers no); exit 0 only if all but the Apptainer limits line are yes.
The implementer may choose: module layout, threads or selectors, test helpers.

## Acceptance

- `uv run --no-project --python 3.9 --with pytest pytest tests/runner -q` passes: configuration and permission refusals; the exact environment key set (`NEMAR_CPUS` present for every job; under Docker or Podman `NEMAR_MEMORY_MB` present for every job, equal to `default_job_memory_mb` when the claimed `memory_mb` is null, with the `memory_default_applied` log line; under Apptainer present exactly when `memory_mb` is not null); a Docker or Podman config without `default_job_memory_mb` refused at start; with a stand-in engine (an executable named `docker` on a test `PATH` that records its arguments and prints fixture ids, as `tests/standin/fake_apptainer.py` does for Apptainer), the exact `ps -aq` commands with both the `nemar.runner` and `nemar.job` filters and the `rm --force --volumes <ids>` commands after a lost lease and at start (a container with another runner's label is never removed); `NEMAR_RUNNER_LABEL` in the key set under an engine; with `sif_pull` false a missing SIF completes the job without any pull command; a pull slower than the lease abandons the job with no heartbeat sent; no heartbeat is sent before the launcher is spawned; a real launcher child is killed when its runner is SIGKILLed (Linux only; elsewhere the test is skipped with that reason); at start a recorded live process group is killed before its job directory is deleted, and a recorded pid whose start time differs is left alone; `doctor`'s two engine lines from the real preflight function; SIF naming and atomic rename; request bodies validated against the pinned schema; a real child process killed at its deadline, on cancel and on lease loss; the memory watchdog on a real child; cleanup after an exception; transport failures (timeout, 5xx, dropped connection) through HTTP fixtures only.
- `uv run pytest tests/contract/test_runner_drift.py -q` passes against the pinned nemar-cli commit.
