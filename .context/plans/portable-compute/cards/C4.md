## Goal

Under Podman the launcher creates the container without starting it, inspects its mounts and devices, refuses (before any user code runs) a container with anything beyond exactly the declared binds, and only then starts it attached; the refusal `podman_unsupported` is lifted only for this path, and a real rootless Podman end-to-end test proves both the refusal and a clean run.

## Context

- `launcher/nemar_launch/runtime.py` (the engine preflight and the Podman refusal), `launcher/nemar_launch/run.py` (how the Docker path builds its argument vector, the four binds, the labels, the limits), `docs/launcher.md` (the pinned isolation flags), `docs/runner.md` ("Containers (Docker and Podman)": engine helpers get only `PATH` and `LANG`, and a rootless engine is unsupported today).
- The real host: GitHub's hosted Ubuntu runners ship Podman and run it rootless as the job's user, so CI is the real host for this card's end-to-end test; a lab host the owner names later only repeats it.
- Rootless Podman needs `XDG_RUNTIME_DIR` (or falls back to a per-user directory); the runner's helpers currently drop it.

## Scope

- `launcher/nemar_launch/run.py`, `launcher/nemar_launch/runtime.py`, `launcher/nemar_launch/codes.py` only if a new detail is needed (prefer the existing `bind_source_unsafe` or `runtime_unusable`; a new word needs a nemar-cli card first: stop and report), `runner/nemar_runner/containers.py` (the helper environment for Podman only), `docs/launcher.md`, `docs/runner.md`, new `tests/launcher/test_podman_e2e.py`, `.github/workflows/ci.yml` (a Podman end-to-end job), `deploy/tapis/apps/nemar-launch.json` (the re-recorded digest, as DM-09 and DM-10 did).
- Not nemar-cli's ADR 0122: report the sentence to change as a patch note for the lead.

## Decided design

Settled:
1. Podman path: `podman create` with the same flags, binds, labels and limits as the Docker path; `podman container inspect <id>` and read `.Mounts` and `.HostConfig.Devices`; the set of mount destinations must equal exactly the four declared binds (sources, destinations and read-only flags compared), and the device list must be empty; anything else removes the container (`podman rm --force --volumes <id>`) and fails the job before the entry runs; otherwise `podman start --attach <id>`.
2. The refusal `podman_unsupported` stays for any engine path that does not go through step 1 (a test pins it).
3. The runner's Podman helpers get `PATH`, `LANG` and the user's `XDG_RUNTIME_DIR` (only when it is the user's own directory, mode 0700); Docker's helpers are unchanged.
4. `tests/launcher/test_podman_e2e.py` (marker `podman`, required in the new CI job, skipped elsewhere with a reason): with a user `containers.conf` that adds a volume, the job is refused before its entry runs and no container remains; the same with an added device; the same with a `mounts.conf` entry if rootless Podman reads one for the user (otherwise documented as covered only for root); with a clean configuration, a tiny real image runs and exits 0 with exactly the four binds.
5. `docs/launcher.md` and `docs/runner.md` say Podman is supported only through this inspection, and name what remains unverified.
The implementer may choose: the inspection's helper structure.
