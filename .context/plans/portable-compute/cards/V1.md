## Decided design

Settled; the ADR states each item with its reason in one line:
1. **Store content digest `nemar.store-content.v1`** of the one channel group a derivative read from a store's level-0 array: SHA-256 over a UTF-8 header and then the physical values. The header is these lines, each ending in a line feed: `nemar.store-content.v1`; `shape C S` (decimal channel and sample counts); `rate H` where `H` is the 16 lowercase hexadecimal digits of the serving rate as an IEEE-754 binary64, big-endian; `unit` followed by a space and the group's unit, or `unit` alone when it has none; one `label` line per channel in stored order, `label` followed by a space and the channel's label, or `label` alone; `data float64-le`. Two rules decide that text, as eegprep-lean's `labels` and `unit` do: labels are all or none (the lines carry labels only when every channel has a non-empty one; otherwise every line is `label` alone), and the unit is shared or none (`unit` carries text only when every channel states the same non-empty unit; otherwise `unit` alone, so an empty unit is no unit, never `unit` and a space). The module's functions take each channel's label and unit as the store states them (text, empty or absent; a list that is not one per channel is refused) and apply both rules themselves. Text is hashed as its UTF-8 bytes exactly as given: no Unicode normalization, no trimming. The values follow: C times S binary64 numbers, little-endian, channel-major (all of channel 0, then channel 1), each computed as `float64(digital) * float64(scale[c]) + float64(offset[c])` with two separately rounded operations (no fused multiply-add). A unit or label that enters the header holding a carriage return or line feed, or a lone surrogate, has no digest (an error, never a guess); the two rules apply first, so text they drop is never examined, and the TypeScript checks for a lone surrogate before encoding because `TextEncoder` replaces one silently. The archived rate never enters it (`original_rate` is not read).
2. **Input digest**: for a Zarr input, `sha256:` and the SHA-256 of the lines `path TAB group TAB content_sha256 LF`, one per store whose group was read in full, sorted by path in code point order (the order of the paths' UTF-8 bytes, which Python's `sorted` gives; JavaScript's default `sort` compares UTF-16 units and disagrees above U+FFFF, so `inputDigest` compares the paths' UTF-8 bytes), each text taken as item 1 takes it; for a BIDS input, `git:` and the 40-hexadecimal source commit the dataset version names.
3. **Derivative key `nemar.derivative-key.v1`**: SHA-256 of the lines `nemar.derivative-key.v1`, then `dataset`, `version`, `recipe`, `recipe_version`, `engine`, `input`, `profile`, `input_digest`, each as `name SPACE value LF`, in that order. Value rules: dataset `^[a-z]{2}[0-9]{6}$`; version and recipe_version `^[0-9A-Za-z._+-]{1,64}$`; recipe `^[a-z0-9-]{1,64}$`; engine `^[0-9A-Za-z._+@-]{1,64}$`; input `zarr` with profile `serving` and a `sha256:` digest, or input `bids` with profile `archive` and a `git:` digest; any other value or pairing is refused. The image digest is recorded with a derivative, never part of its key.
4. **Retention classes**: `canary` expires 30 days after it is stored; `catalog` is kept until a later `catalog` derivative of the same dataset, recipe, input and profile is promoted, and then expires 30 days after that; `published` never expires and only the owner sets it. Every derivative starts as `canary`. No code path mints a DOI: a future, separately reviewed owner-only action does, for a `published` derivative only.
5. **Where it lives**: a private R2 bucket of its own, objects under `d/` plus the key plus the product's relative paths, immutable once stored; never the serving copy, never the dataset repository, never the 30-day results bucket.
6. **What it says**: every derivative carries `GeneratedBy` (recipe, version, image digest, job id, the nemar-process build) and `SourceDatasets` (dataset id, version, the version DOI when there is one), a citation string, and for the `serving` profile the one sentence declared once in the module: "Computed on NEMAR's Zarr serving copy (EEG capped at 250 Hz, 16-bit), not on the archived recordings." It names EEG only, which is true of every derivative the store can take (the one Zarr-input recipe reads only a store's EEG group); the ADR says the cap is per modality and that the card which first lets a recipe read a group of another modality adds that modality's sentence to the module, with an amendment to the ADR, before any such derivative is stored (amendment of 2026-11-14: the module comment states this rule, not an open point).
7. **Known limit**, stated in the ADR: until the converter writes each store's content digest at commit (phase Z), the digests are computed by the recipe from what it read and recorded in its signalJourney record; the platform records them and cannot verify them. So a recorded input digest keys a derivative only when every check holds: for either input, the job's dispatched spec named no `--recording` (the record cannot say a run was a subset) and no row of its recordings table ended `out_of_memory`, `internal_error`, `disk_error` or `time_budget` (a rerun under the same key could differ; a deterministic failure may be keyed); for a `zarr` input also, the dataset record's `stores_unread` (a list of the store paths not read in full, never a count) is an empty list, its `stores_content` is non-empty, the paths of those rows are its `input.stores`, each once, and `inputDigest` of those rows equals its stated `input_digest`. The ADR states these checks; card V1b applies them, and card Q0b's stamp stores a Zarr digest only after the first three Zarr checks.
8. The module exports `STORE_CONTENT_FORMAT`, `storeContentHeader`, `storeContentSha256`, `inputDigest`, `derivativeKeyText`, `derivativeKey`, `RETENTION_CLASSES`, `CANARY_DAYS = 30`, `SUPERSEDED_GRACE_DAYS = 30`, `SERVING_PROFILE_SENTENCE`, and a validator for the key fields.
9. `derivatives-vectors.json` holds, and the test asserts:
   - store content, shape 2 by 3, digital `[[1, -2, 3], [32767, -32768, 0]]`, scale `[0.1, 0.25]`, offset `[0.0, -12.5]`, rate 250.0, unit "µV" (U+00B5), labels "Fz" and "Cz": header bytes ending `rate 406f400000000000\nunit µV\nlabel Fz\nlabel Cz\ndata float64-le\n` and digest `0c268ca3444e5c884afb5475ae13b6bc3170869776b2e4b0118205f2f08f84cd`;
   - the same values with no unit and no labels: `6bff43f9934204b3bf515734cc563ef72da392cc594dc2cdcbd317d9e98f58fd`;
   - partly labeled: the same values and unit with labels "Fz" and none: header bytes ending `unit µV\nlabel\nlabel\ndata float64-le\n` (never `label Fz\nlabel`) and digest `424c2a59e3e313b591c3b5516e8522717df6add915d6508646f323338d95adc0`; with units "µV" and "mV", or with both units empty and labels "Fz" and "", the digest is the second vector's;
   - the input digest of the one row (`sub-01/eeg/sub-01_task-rest_eeg.edf`, `eeg`, the first digest): `sha256:bea77ea8a233ae2507f192e48548af37b8acf01c8abb0e65143ac3178e44bc0b`;
   - code point order: the input digest of two rows (group `eeg`, the first digest) whose paths are `sub-01/` then U+FF61 and `sub-01/` then U+1F600, given in either order, is `sha256:4bf7b0ab0a746ebe769759f4989df1ac1c810eaea360c891d76abd6162508c53` (the U+FF61 row first);

   - the same with input `bids`, profile `archive`, input digest `git:` and forty `a`: `da56eaa8eb746589c8bd6cb98114ceb5555db6d14a1092707869526d9aba15e1`.
The implementer may choose: the ADR's prose, helper names inside the module.
