## Goal

`nemar-recipe run nemar-ica` produces, per recording, the ICA decomposition of the floor-cleaned, ASR-repaired, average-referenced data through eegprep (pAMICA's torch engine on the CPU by default and on a GPU when the runner grants an idle one, or the AMICA binary pAMICA v0.4.0 ships as the CPU fallback engine, which starts from the clock because nothing writes it a seed, and so is recorded as not bit-reproducible), with ASR's state, the weight files written so float64 round-trips, ICLabel's probabilities, and a signalJourney record that names every parameter, version, digest, convergence fact and the device that ran, and it never runs an engine other than the one asked for and never fails because a GPU is busy. The decomposition is pAMICA's claim (the owner, Q31: "That is the pamica's promise, we accept it as is, but mention that it is done via pamica, and also mention which pipeline of pamica, to make the reproducibility possible"): the record and the docs say pamica computes it, name its version, backend and pipeline, every setting and the fixed seed, and claim no equality with EEGLAB's AMICA.

## Decided design

Settled:
1. **Identity.** Recipe `nemar-ica`, `RECIPE_VERSION` 1.0.0, label `nemarica`, inputs `bids` and `zarr` exactly as the floor's `--input` after Q0.
2. **Steps per recording**, each an eegprep call: the floor's chain with its parameters (its decisions are recorded as this record's first steps); remove the floor's bad channels; `clean_asr(EEG, return_state=True, maxmem=1024)` with eegprep's other defaults, on an EEG that carries its `chanlocs` (so the state names its channels), where a `UserWarning` from PX-04's `maxmem` check fails that recording with reason `asr_maxmem` and writes nothing for it (a state that cannot reproduce its data is never written; 1024 MB covers 64 channels up to a lookahead of about 10000 samples); `pop_reref(EEG, [])`; `pop_runica(EEG, icatype=..., reorder='on', ...)` (eegprep's default, passed and recorded because `EEG['etc']['pamica']` does not hold it) with rank `pcakeep = min(N_good - 1, 64)` where `N_good` is the channel count after the floor's removal; `pop_iclabel(EEG, "default")`. ICA fits the ASR-repaired copy (issue #5's default). A `PamicaFitError` (a degenerate stop: no ICA field set) fails that recording with reason `ica_degenerate` and writes nothing for it.
3. **Options.** `--ica-engine pamica|amica15` (default `pamica`), `--ica-device auto|cuda|cpu` (default `auto`; `amica15` takes only `cpu`, any other pair is exit 2), `--ica-threads N` (default 1), `--ica-max-iter N` (default 2000; recorded, so a short test product says so), `--time-budget-s N`. `auto` resolves once, at start: to `NEMAR_DEVICE` when it is set (a value other than `cpu` or `cuda` is exit 2), with `NEMAR_DEVICE_REASON` as the reason; otherwise to `cuda` when `torch.cuda.is_available()` (reason `gpu_present`), else `cpu` (reason `no_gpu`); a `cuda` resolution whose GPU is not visible in the container becomes `cpu` with reason `gpu_not_visible`. `pamica` passes `n_models=1, n_mix=3, max_iter, block_size=131072, seed=5489, device, threads, pcakeep` and no other setting (eegprep applies its `runamica15` table to the rest, as PX-03 merged it, and the record states each value), and never `fix_init` (pAMICA 0.4.0's torch backend does not take it; the start is pAMICA's draw from the fixed seed); `amica15` passes `num_models=1, num_mix_comps=3, max_iter, pcakeep, max_threads=threads` and the binary `/opt/amica/amica15`, and never `seed` or `fix_init` (eegprep would write either into the binary's parameter file).
4. **Preflight (exit 8, nothing written):** an explicit `--ica-device cuda` with `torch.cuda.is_available()` false gives `engine_unavailable: no_gpu` (`auto` never exits for lack of a GPU: it resolves to `cpu`); `pamica` or `torch` not importable gives `no_pamica`; `amica15` whose binary is missing, or whose SHA-256 differs from `/opt/amica/amica15.sha256`, gives `no_amica15`. No other engine is ever substituted; the device changes only under `auto`, by item 3's rule and card Q1c's, and is always recorded.
5. **Files per recording** (`desc-nemarica`): `_channels.tsv` (the floor's channel decisions, which define the good-channel set), `_asr.json` (`state_to_json` from `eegprep.plugins.clean_rawdata.asr_state`, written by the recipe as canonical JSON: `json.dumps(..., sort_keys=True, separators=(",", ":"), allow_nan=False, ensure_ascii=True)` plus one newline, so its SHA-256 is stable), `_unmixing.tsv` (`icaweights @ icasphere`, components by channels), `_weights.tsv`, `_sphere.tsv`, `_mixing.tsv` (`icawinv`), each through `write_matrix_tsv` with channel labels or `IC001` style labels as column headers; `_components.tsv` (`component`, `variance_pct`, the seven ICLabel class probabilities, fixed decimals); `_ica.json`; `_signalJourney.json`. `LLt` is never stored. `extensions.nemar.outputs` lists each file's `sha256`, `size`, `shape`, `dtype` and labels.
6. **What the record says** (`extensions.nemar` and `_ica.json`): engine (`pamica-torch` or `amica15`); for `pamica` a `pamica` block that is `EEG['etc']['pamica']` copied whole, every key under eegprep's name and value, never renamed or recomputed (the top-level `iterations`, `stop_reason`, `did_converge` and `rank` are copies of it), so the record names the pamica pipeline as Q31 asks; `reorder` `on`; eegprep, pamica and torch versions; `start` (`pamica_seed` for `pamica`; `amica15_clock` for `amica15`); `bit_reproducible`: true for `pamica` on `cpu` with 1 thread (pamica's promise as eegprep states and tests it: the same seed, data, settings, pamica and torch versions, float64, one machine), null for `pamica` on `cuda` or with more than 1 thread (eegprep does not state it, and pAMICA's own statement for CUDA float64 is unmeasured until the pAMICA workstream's PA-07), false for `amica15` (it starts from the clock); device and, on CUDA, `torch.cuda.get_device_name(0)`, dtype `float64` (the AMICA fallback states the 32-bit data file eegprep writes for it: on a real recording, float64 after ASR and re-referencing, the binary sees data rounded to float32, about 1e-7 relative, which the float32-stored EEGLAB sample of E1 does not show), ASR's `maxmem`, seed, `n_models`, `n_mix`, `max_iter`, `block_size`, threads, `pcakeep` and rank, reference `average`, the good-channel set, iterations, stop reason, `did_converge` (from the stop reason, never `converged_`), final and best log-likelihood and best iteration, the ASR state's SHA-256 (of the `_asr.json` bytes), ICLabel's version and the SHA-256 of its network weights file, the input profile, and for `amica15` the binary's SHA-256; and the device facts: `device_requested` (`auto`, `cuda` or `cpu`), `device` (the one that ran), `device_reason` (item 3's reason, or `requested` for an explicit device), `fallback` (true exactly when `device_requested` is `auto` and `device` is `cpu`), the torch version and `torch.version.cuda`, threads, and `image_flavor` (from `/opt/nemar/flavor`, null outside an image); the dataset-level record adds `devices` (recordings per device). `engine_extra` adds `ica_engine` to the engine stamp and never the device, so a GPU run and a CPU run carry the same engine stamp and match the registry's tuple either way (card Q1a).
7. **The image workflow's cases (E1 informational, Q31, Q32):** in the CPU flavor's end-to-end job (the one that runs `tests/e2e`), on the repository's EEG fixture recording at full length, 1 thread, CPU float64, `max_iter` 2000, the test prints `E1R (informational) min=<x> median=<y> amari=<z> reference: min>=0.95 median>=0.99 amari<=0.05` for `pamica` against the image's `amica15` (Hungarian-matched absolute correlations of the sensor-space unmixing rows; the Amari distance as PX-03's test computes it, `amari_distance(pamica_unmixing, pinv(amica_unmixing))` from eegprep's `tests/test_ds003061_stage_parity.py`, written again in the test because eegprep's tests are not installed) and asserts nothing about those numbers; no document or record turns them into a claim. The same job runs `amica15` twice on the fixture cut as in the Acceptance's tiny run (`--ica-max-iter 50`) and asserts that the two weight files are NOT byte-identical, as the unseeded binary implies and the record's `bit_reproducible: false` says; identical files stop the card (the record would be wrong). In the CUDA flavor's job, with no GPU visible (as PX-06's smoke runs it), one tiny `pamica` run in the container records `device` `cpu`, `device_reason` `no_gpu`, `fallback` true, `image_flavor` `cuda` and torch `2.12.1+cu129`: the image and path the registry uses.
8. **Docs** (`docs/recipes.md`, the `nemar-ica` section): pamica computes the decomposition, through eegprep; the section names the pamica pipeline in the record's words (pamica 0.4.0, backend `AMICATorchNG`, pipeline `pamica.AMICA(backend='torch').fit`, device, dtype float64, threads, seed 5489, `reorder` on) and every setting that differs from pAMICA's own defaults, as eegprep's table supplies them; reproducibility is pAMICA's (the same versions, settings, seed and data on the CPU in float64 with one thread give identical files), a CUDA record states no bit reproducibility, and the `amica15` fallback is not bit-reproducible; a run with another seed gives a different decomposition beyond the strongest components (on EEGLAB's 32-channel sample, with eegprep's defaults, two seeds agree at minimum 0.526, median 0.936, PR 617's measurement); E1 is informational and varies from run to run because EEGLAB's binary starts from the clock, and no sentence claims equality with EEGLAB's AMICA; `did_converge` is false by construction at the defaults (no stopping test is enabled), so `stop_reason` is the field to read; ASR's `maxmem` is fixed and recorded because a smaller or missing value makes the cleaned data depend on the machine; a change of the pamica pin, the CUDA flavor's torch or the `amica15` binary is a new `RECIPE_VERSION` (item 10).
9. **The eegprep pin.** No release holds PX-03 and PX-04, and `develop` says `0.5.0` like the PyPI release that has neither, so a commit pin must name its commit or two eegprep builds share one engine string, one stamp tuple and one derivative key.
   - No such release at dispatch (the state of 2026-11-14; the owner's QA remark allows a `develop` pin): require `eegprep[mne,pybids,picard,torch,pamica] @ git+https://github.com/sccn/eegprep@edf694c8344b9c4c68672eac3acf9a819f1462a8` (PR 617's merge commit; a later commit only if the lead names one, never a branch or a short hash). One helper gives eegprep's version as `<version>+<commit>`, the commit read from the installed distribution's `direct_url.json` (`vcs_info.commit_id`, 40 hexadecimal digits), the rule of Q0's `reader_string`, and the bare version when there is none (an index install); the engine stamp, each step's `software.version` and `nemar-recipe version` all use it, so records, stamps and the registry say `eegprep@0.5.0+edf694c8344b9c4c68672eac3acf9a819f1462a8` (54 characters, within the stamp's 64 and ADR 0123's engine pattern). The PR is ready for review and may merge on this pin.
   - A release holding both exists at dispatch (QA answered "release"): require `eegprep[mne,pybids,picard,torch,pamica]==` that version and move eegprep-lean to the same release if PyPI has it (PX-08's note); the helper adds no suffix.
   - The release comes after this card merged: a PX-08-style card moves the pins; the engine text loses its suffix (a new engine and new stamp tuples, which is correct) and that card re-checks the floor's golden decisions.
   - `COMMON_VERSION` stays 1.0.0 under Q35's rule: `device.py` adds fields only to `nemar-ica`'s records, which no released recipe wrote, and the helper changes no byte any released (recipe, version, input) wrote, because a released image installs eegprep from an index and its text keeps the bare version; the `+<commit>` text appears only in records no release wrote. The Acceptance proves both halves.
10. **The product is a derivative (ADR 0123, V1; stored by V1b).** Its key is the platform's, computed by V1b from the stamp: dataset, version, `nemar-ica`, `1.0.0`, the engine of item 9, then `bids` with `archive` and the `git:` source commit, or `zarr` with `serving` and the `sha256:` digest of the stores read in full; so the Zarr input block (`stores`, `stores_content`, `stores_unread` as a list, `input_digest`) is written by the same common code as the floor's after Q0, never a copy. This card never writes into the derivative store or any bucket, never computes or records a derivative key, never edits `shared/contract/derivatives.ts` or its vectors, never writes into the serving copy or a dataset repository, and names no DOI; the device, GPU name, threads, image digest and `ica_engine` never enter `engine.package` or `engine.version`. Because the key names eegprep alone, ADR 0123 decision 2's duty falls on `RECIPE_VERSION`: a change of the pamica pin, the CUDA flavor's torch or the `amica15` digest bumps it, and a test fails when `uv.lock`'s pamica or `cu129` torch differs from the constants the recipe holds. Only the registry's invocation (`pamica`, `max_iter` 2000, threads 1, device `auto`) is dispatched by the platform; the options that change values (`--ica-engine`, `--ica-max-iter`, `--ica-threads`) are for manual and test runs, and a card that lets a dispatch pass one must first make it change the key (patch note for V1b and Q1a). `asr_maxmem` and `ica_degenerate` are deterministic failures, which V1b may key; the transient words of ADR 0123 decision 7 (`out_of_memory`, `internal_error`, `disk_error`, `time_budget`) name only transient failures.
The implementer may choose: module layout under `nemar_ica/`, helper names, the column labels' exact spelling (documented in `docs/recipes.md`).
