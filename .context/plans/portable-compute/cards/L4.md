## Goal

Name, with measurements from the CI host where it happens, why the launcher sometimes records a container killed at its memory limit (exit 137) as `runtime_error` with detail `entry_failed` (launcher exit 13) instead of `out_of_memory` (launcher exit 14); then, only if the cause is in the launcher, fix it with a deterministic test that fails without the fix, and leave the end-to-end test's expectation untouched.

## Context

- The failure (issue #31): `tests/e2e/test_docker_launch.py::test_a_container_that_outgrows_its_memory_limit_is_killed_and_recorded` (a 128 MB limit, an entry that appends 16 MiB chunks) in CI's `docker backend (end to end)` job.
  Six failed attempts on 2026-11-14 on five pull requests' branches: S1R (PR 29, run 43614511358), L1 (PR 30, run 43615872559), S4 (PR 33, run 43621496723), PX-07 (PR 37, runs 43634937389 and 43638068665), Q0 (PR 38, run 43656425486); push and pull_request runs alike, on changes that touch no launcher code, each passing when rerun.
- How a 137 is classified today, read at the runner epic head 85d3e3ec: `run.run_container` maps the `docker run` client's exit; 137 is `out_of_memory` only when `oom_check()` is true, else `runtime_error` / `entry_failed`.
  For Docker and Podman, `__main__.py` passes `oom_check = functools.partial(runtime.oom_killed, runtime_path, container, env)`, and `runtime.oom_killed` runs ONE `container inspect --format {{.State.OOMKilled}}` (10 s timeout) right after the client returned, and returns true only for exit 0 with the output `true`: a `false` answer and a failed or timed-out inspect are the same `False`, and nothing about the read is logged.
- Ruled out by reading: a removal race.
  The container has a unique launcher-made name (`nemar-launch-` and 16 hexadecimal digits) and no `--rm` (pinned in `tests/launcher/test_runtime_docker.py`), and `runtime.remove_container` runs in a `finally` after `run_container` has returned, so the inspect always finds the stopped container.
- The two failing logs, read with escape sequences stripped (job 132579187269 of PX-07's run 43638068665, job 132635834162 of Q0's run 43656425486): identical launcher lines, `engine: can enforce cpu, memory and pids limits`, then `run: the container exited with 137` and `failed: runtime_error (entry_failed)` in the same second.
  Ten job logs of that day (the six failed attempts and four passing reruns) all ran on the hosted image `ubuntu-26.04` version 20261111.196.1 with Docker 29.4.2, containerd v2.4.2 and runc 1.5.2, and the memory test took 0.47 to 0.62 s in failed attempts and 0.55 to 0.60 s in passing ones: the logs show no host-image, engine-version or timing difference.
- The race this card tests first (a hypothesis, not yet measured): Docker sets `State.OOMKilled` when its daemon handles containerd's out-of-memory event, which is a separate event from the container's exit (the lead's understanding of the daemon's design, not re-read for 29.4.2).
  The attached `run` returns on the exit; when the daemon handles the out-of-memory event after the exit, the single immediate read sees `false` (H1, a late event).
  The logs cannot tell H1 from two other readings: the engine never learns of the kill (H2, a lost event, below the launcher: containerd's shim, cgroup v2 or the kernel), or the inspect itself failed (H3).

## Decided design

Settled:
1. **Round 1, the measurement.** On the draft PR into `feature/runner-epic`, the temporary workflow runs the harness on both runner images: 300 iterations per image of the memory test's launch, each with the launcher's own argument vector and image for that test (128 MB, 1 CPU, the eater).
   Per iteration it records: the client's exit status; the first `container inspect --format '{{json .State}}'` taken where the launcher takes it (at once after the client returned), with `OOMKilled`, `ExitCode`, `Error` and the inspect's own exit status; then `{{.State.OOMKilled}}` re-read every 20 ms for up to 5 s, giving the delay of the first `true` or `never`; and the container's events from `docker events --since <start> --until <end> --filter container=<name> --format '{{.TimeNano}} {{.Action}} {{json .Actor.Attributes}}'` (the order of `oom` and `die`).
   Once per job it prints the kernel release, `docker info --format '{{.CgroupVersion}} {{.CgroupDriver}}'`, and the engine, containerd and runc versions.
   It ends with one line per image: `DIAG image=<label> n=<n> exit137=<a> first_false=<b> late_true=<c> delay_ms=<min>/<median>/<max> never_true=<d> no_oom_event=<e> inspect_failed=<f> die_before_oom=<g>`.
2. **Waiting for it.** The diagnostic job is this card's own measurement, expected under 15 minutes, so the worker may wait for it (an exception to the preamble's rule about CI watches): `gh run view` at most once a minute, for at most 20 minutes; past that, report the run id and stop for the manager.
3. **The pre-registered reading**, per image, over the iterations whose first read was not `true` (`first_false`): H1 (late event) when every one of them reads `true` within 5 s; H2 (lost event) when any of them never reads `true` within 5 s, its events saying whether the engine emitted an `oom` event at all (reported, not decisive); H3 (failed read) when any first inspect exited non-zero or timed out; H0 (not reproduced) when `first_false` is 0, after which the harness runs once more at 1000 iterations per image.
   Any H2 decides the card (stop conditions), whatever else is seen; H1 and H3 may occur together, and round 2 covers both.
4. **Round 2, the fix (H1 or H3 only).** `runtime.oom_killed` reads as today; when the answer is not `true` (a `false`, a failed inspect or a timeout), it reads again every 0.1 s until an answer is `true` or `OOM_SETTLE_SECONDS` have passed since the first read, and returns true if any read said `true`.
   `OOM_SETTLE_SECONDS` is the smallest multiple of 0.5 s that is at least 1 s and at least 4 times the largest delay round 1 measured on either image.
   Each read keeps `CONTAINER_INSPECT_SECONDS`.
   A SIGTERM the launcher receives during the re-reads ends them at once and the answers so far stand.
   The launcher logs the outcome once, `oom: the engine says the container was killed for memory (<k> reads, <t> s)` or `oom: the engine does not say the container was killed for memory (<k> reads, <t> s, <f> failed reads)`, with no name, host or path.
   Nothing else changes: the re-read happens only after a 137 and only under Docker or Podman (Apptainer passes no `oom_check`), and the command line, the name, the absence of `--rm` and the removal after the read stay as they are.
5. **The deterministic test.** `tests/standin/fake_docker.py` gains `<rec>.oom-after` holding a count N: the first N `container inspect` calls print `false` and later ones `true` (its docstring says so).
   New tests in `tests/launcher/test_runtime_docker.py`: (1) a 137 whose engine says `true` only on the third read is `out_of_memory`, launcher exit 14, with three inspects (it fails at the base: one read, exit 13); (2) a 137 the engine never calls an out-of-memory kill is `entry_failed`, exit 13, after more than one inspect, finished within `OOM_SETTLE_SECONDS` plus 2 s of the client's exit; (3) a first inspect that exits non-zero followed by `true` is `out_of_memory`.
   The existing tests stay unchanged and keep passing: a 137 called an out-of-memory kill at once takes exactly one inspect; a non-137 exit takes none.
6. **Evidence on the fixed head, then cleanup.** Before the cleanup commit, the harness runs once more on both images and counts the launcher's own outcome per iteration (exit 14 against 13): quoted as a reading, not a gate.
   Then the temporary workflow and harness are deleted, and `git diff --stat origin/feature/runner-epic...HEAD` lists neither.
   `docs/launcher.md` says, beside "An exit status of 137 is `out_of_memory` only when `OOMKilled` is true", how long the launcher waits for the engine to say so and why (the engine reports the kill and the exit as two events), with the measured largest delay.
The implementer may choose: the harness's structure (a temporary instrumented `oom_killed` driven through the end-to-end test's rig, or a standalone script built on `runtime.build_argv`), provided every iteration uses the launcher's own argument vector and image for the memory test and records item 1's facts.

## Stop conditions

- H2 on either image: the engine did not say within 5 s that it killed the container for memory, a fault of the CI host's engine, control groups or kernel that no bounded re-read by the launcher can repair.
  Stop after round 1 and report the counts per image and whether those iterations had an `oom` event.
  Do not change the end-to-end test's expectation: a gate's expectation changes only through the owner.
  The options for the manager to put to the owner as one question: A the end-to-end test also accepts `entry_failed` with entry exit 137 when the engine never reported the kill as one for memory (weakens the gate); B pin the job to the runner image where H2 did not occur, if the matrix shows one; C a later card in which the launcher reads the kernel's own count from a control group it owns; D keep rerunning.
- H0 after the 1000-iteration rerun: stop and report (the loop lacks something the suite has; the manager decides whether to run the suite's own order instead).
- The bound of item 4 would exceed 5 s: stop and report the measured delays (a 137 that was not an out-of-memory kill would wait longer than that for its record).
- The fix would need a new failure word or detail (a nemar-cli card comes first), a change to the engine command line or `--rm`, or removing the container before the read: stop.
