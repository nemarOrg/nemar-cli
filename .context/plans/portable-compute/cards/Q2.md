## Goal

A consumer can apply the floor's bad-window decisions directly to the samples the QC read (for Zarr input, the serving copy's level-0 sample index) without converting seconds, and NEMAR's catalog can show a dataset's QC from one small file with a declared schema instead of parsing the signalJourney record.

## Decided design

Settled:
1. **Sample mask**, per recording, `<entities>_desc-nemarfloor_samplemask.tsv` beside `_badsegments.tsv` (which stays), with columns `start_sample` (0-based index into the samples the floor read), `stop_sample` (exclusive), `label` (`bad_window`) and `nemar_reason`, one row per maximal run of False in the window step's sample mask, in order; absent when the window step was skipped, as `_badsegments.tsv` is. The per-recording record adds `extensions.nemar.mask_grid = {"n_samples", "rate", "profile"}`, where `rate` is the rate of the samples read (the store's serving rate for Zarr input) and `profile` is `serving` or `archive`. A test proves every row of the mask equals the matching row of `_badsegments.tsv` multiplied out by `rate`.
2. **QC summary**, per dataset, `desc-nemarfloor_qcsummary.json`, valid against `docs/schemas/qc-summary.v1.json` and at most 65,536 bytes: `format` (`nemar.qc-summary.v1`), the identity (dataset id, version, recipe, recipe version, input kind, profile), `describes` (for Zarr input exactly "QC describes NEMAR's Zarr serving copy (EEG capped at 250 Hz, 16-bit), not the archived recordings."; for BIDS input exactly "QC describes the dataset's recordings as archived."), the counts, the four distributions of the dataset record (percent good channels, percent good samples, line-noise excess before and after) with `n`, `min`, `median`, `max` and the same bins, `not_processed` (path, status and code of every failed or skipped recording, at most 200 with `not_processed_truncated`), and `record_sha256` (the SHA-256 of the dataset record file's bytes).
3. **Aggregate** copies each input's sample masks byte for byte and rebuilds the summary from the merged rows and record, so a merged summary equals the summary of one run over the same recordings, apart from `record_sha256`.
4. **Version 1.0.1**, a patch, for both inputs (one recipe, one version; Context says why): `RECIPE_VERSION`, `PINNED_RECIPE_VERSION`, and every sentence of `docs/recipes.md` that states the floor's version (the steps heading, `pipelineInfo.version`, the `engine_version` example, the Zarr-input paragraph, whose reason becomes this bump's).
   `COMMON_VERSION` stays 1.0.0: nothing under `common/` changes (`naming.product_path` and `naming.dataset_path` make both names, and `write_product`'s `nemar_extra` carries `mask_grid`).
   `docs/recipes.md` "For the next recipe" gains one sentence after Q0's: this change adds files and fields to the directory input's records, which a released image wrote at 1.0.0, so it is the patch bump to 1.0.1 for both inputs, and its golden decisions moved only by the version and the plan hash.
   Determinism covers both new files (byte-identical across two runs, the summary after removing nothing, since it holds no clock).
5. **The golden files under a bump.** No step is added, removed or given another parameter, no rule, threshold or skip changes, and the mask is written from the window step's existing sample mask, so the resolved plan differs from 1.0.0's only in its version.
   The golden directory is renamed to `nemar-floor-1.0.1` and regenerated with `scripts/make_floor_golden.py`, whose `GOLDEN` and docstring name the new directory: `channels.tsv` and `badsegments.tsv` stay byte-identical, and in `decisions.json` exactly two values change, `recipe.version` (1.0.1) and `plan_hash`.
   Two new tests in `tests/recipes/test_golden_decisions.py`: the fixture record's resolved plan (`plan.resolved_plan`) with `recipe_version` set back to `1.0.0` hashes (`plan.plan_hash`) to the 1.0.0 golden hash `sha256:ffa6a154580dd7099bb4f2a6a5bf7a9b3f1f2ffc6a99e9a2603124702ebe35fd`, written in the test as a literal (the plan moved only by its version); and the golden directory's name is `nemar-floor-` followed by `RECIPE_VERSION`.
   The module docstrings of the test and the script say what a bump does: the golden files are regenerated into the directory of the new version, and a bump that changes no decision changes only `recipe.version` and `plan_hash` in `decisions.json`, the channel and bad-segment tables staying byte-identical.
The implementer may choose: helper names, how the schema file is laid out.
