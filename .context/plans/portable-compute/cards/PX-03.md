## Goal

`eegprep.pop_runica(EEG, icatype='pamica', ...)` decomposes with pAMICA's torch engine, fills the EEGLAB ICA fields so the data reconstruct, records its run facts in `EEG['etc']['pamica']` including pAMICA's backend and pipeline, is bit-reproducible for a fixed seed in float64 on CPU, says in its docstring and docs that pAMICA computes the decomposition (version, backend, pipeline), and prints, where EEGLAB's binary runs, an informational comparison with EEGLAB's AMICA (`icatype='runamica15'`) that asserts nothing (plan 2.9, E1; the owner, Q31: "That is the pamica's promise, we accept it as is, but mention that it is done via pamica, and also mention which pipeline of pamica, to make the reproducibility possible").

## Decided design

Settled:
1. `eeg_pamica(EEG, *, n_models=1, n_mix=3, max_iter=2000, block_size=131072, seed=5489, device="cpu", threads=1, pcakeep=None, **amica_options)`; `pop_runica` maps `icatype='pamica'` to it; an `ImportError` for `pamica` or `torch` names the `pamica` extra.
2. Parameters a caller does not pass take eegprep's `runamica15` values as `_AMICA_DEFAULTS` states them (which differ from upstream `runamica15.m` in `use_min_dll`, `use_grad_norm`, `invsigmin` and `mineig`; the docs call them eegprep's defaults), for each name pAMICA's torch backend also takes: `lrate=0.05`, `minlrate=1e-8`, `rho0=1.5`, `do_newton=True`, `newt_start=50`, `use_min_dll=False`, `use_grad_norm=False`, `do_mean=True`, `do_sphere=True` (where pAMICA spells a name differently, map it and say so in the docstring). `block_size` is pAMICA's own (131072), because EEGLAB's 128 is the Fortran program's per-thread block and means something else.
3. Threads: `torch.set_num_threads(threads)` and `threadpoolctl.threadpool_limits(threads)` for the run, both restored afterwards; the default is 1; the docstring says a larger count is reproducible only on the host where it was measured.
4. Fields: `icaweights @ icasphere` equals the sensor-space unmixing pAMICA applies (`transform` of the data equals `icaweights @ icasphere @ data` within 1e-10 relative); `icasphere` is `get_sphere()` (the identity when pAMICA ran with `do_sphere=False`); `icawinv = pinv(icaweights @ icasphere)`; `icachansind` the channels used; components in pAMICA's order, sorted by variance only when `pop_runica`'s `reorder` asks for it, as for the other engines.
5. `EEG['etc']['pamica'] = {version, backend, pipeline, torch, device, dtype: "float64", seed, n_models, n_mix, max_iter, block_size, threads, pcakeep, the step-2 parameters as used, iterations (len(ll_history_)), stop_reason, did_converge, final_ll, best_ll, best_iter}`, where `did_converge` is true exactly when `stop_reason_` is neither `max_iter` nor one of pAMICA's degenerate reasons; a degenerate fit raises a typed error and sets no ICA field. `backend` is the backend pAMICA fitted with, as passed to `pamica.AMICA(backend=...)` (`"torch"`); `pipeline` is the module-qualified class name of the engine object pAMICA fitted (`model.model_`, today `pamica.torch_impl.core.AMICATorchNG`), so a reader can rerun exactly that engine with the recorded settings and seed.
6. Check E1 (plan section 2.9; informational since Q31 and Q32, never a gate here): on `sample_data/eeglab_data.set` (the repository's copy), with `n_models=1`, `n_mix=3`, `max_iter=2000`, float64, 1 thread, each engine through `pop_runica` with its defaults, the test computes the Hungarian-matched absolute correlations between the rows of the sensor-space unmixing matrices (`icaweights @ icasphere`) of `pamica` and `runamica15` and their Amari distance, prints one line `E1 (informational) min=<x> median=<y> amari=<z> pamica_s=<t1> amica_s=<t2> reference: min>=0.95 median>=0.99 amari<=0.05` to the terminal (with `capsys.disabled()`), and asserts nothing about those numbers. It skips with the stated reason "the shipped AMICA binary cannot run on this host" when `is_amica_available()` is false, and fails instead of skipping when `EEGPREP_REQUIRE_AMICA=1` (so the macOS job still fails when the binary cannot run).
7. A local, informative run (not a verdict; E1 has none): on a host that cannot run the shipped binary, the implementer may point `AMICA_BINARY` at pAMICA v0.4.0's `amica15-macos-arm64` release asset (checked against its published `.sha256`), labels those three numbers "informative, pAMICA's arm64 build of amica15", and quotes them beside the CI line.
8. Documentation and record duty (the owner, Q31): the `eeg_pamica` docstring, `pop_runica`'s help text and the docs' ICA section say that pAMICA computes the decomposition and name the pinned pAMICA version, its backend and pipeline (item 5's values), the settings that differ from pAMICA's own defaults, and the seed; they state reproducibility as pAMICA's (the same version, backend, settings, seed, device, dtype and thread count give identical weights) and make no claim of agreement with EEGLAB's AMICA beyond saying that an informational comparison exists and varies with the binary's clock-seeded start.
The implementer may choose: helper names, the test's matching code (`scipy.optimize.linear_sum_assignment`).
