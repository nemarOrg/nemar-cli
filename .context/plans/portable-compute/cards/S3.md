## Goal

The owner holds one document that proves each item of the bar with links to its evidence and lists, in order, the exact commands and the exact diff with which the owner alone turns on runner jobs in production for QC only (`nemar-floor-zarr`) with a live cap of 2, plus the acceptance check of five production runner jobs `finished` and zero `runner_lost`. No agent flips a switch, writes a production secret, stores a policy, registers a production runner or dispatches a production job.

## Context

- Dark switches stay out of `backend/wrangler-sccn.toml` until the owner adds one in a reviewed pull request that edits `backend/test/compute-switches-flag.test.ts` (`AGENTS.md`); the owner authors that change. `COMPUTE_PIPELINES_DISPATCH_ENABLED` (the Tapis daily dispatcher) stays off: runner jobs are dispatched by hand.
- Rollback hazard (ADR 0121): a Worker from before the epic reads a stored `policy.runners` as unreadable and fails every compute path closed. Rule: store it only when the production Worker's previous deployment also reads it, that is, after a second release containing the epic has been deployed (`bunx cfman wrangler --account sccn deployments list -c backend/wrangler-sccn.toml`, the two newest).
- The code default today is `RUNNERS_POLICY_DEFAULT = { maxLiveJobs: { cpu: 64, gpu: 8 } }` (`shared/contract/compute.ts`); the bar says the cap starts at 2. OQ2 decides between lowering the code default (option A, no stored key needed) and storing `policy.runners` after the rollback rule holds (option B).
- ADR 0122 decision 6: a rootful Docker group is allowed only on a single-tenant lab machine recorded in the gated systems inventory (card W2 records it); otherwise the production runner uses Apptainer with `doctor`'s limits line yes.
- The owner (2026-11-14): the workstations are shared with other people's work. That puts decision 6's single-tenant premise in question for workstation B; the owner answers ON of `cp2-note-N.md` (A Apptainer, recommended; B rootless Podman after C4; C rootful Docker only if no other person has an account on the host or is in its `docker` group). The runbook writes the runtime of that answer and nothing else.
- The shared-machine rule (cards L2 and L3, `cp2-note-N.md`): the runner claims only idle capacity (free memory above a reserve, load per CPU, free scratch; the registration stays the ceiling), runs itself and its children at the lowest CPU and I/O priority, never preempts a started job, and stops claiming when a `pause` file exists in its reservation directory; GPU jobs are not part of this flip (the GPU cap stays 0).
- S3a's section 5 (the ADR 0118 A1c registration block) must be resolved by the owner first (an amendment to ADR 0121, or settling the nemar-process#9 items).
- Datasets: public, named, EEG, 2 to 6 stores, with a Zarr copy whose source check passes (DM-02's criteria); never `nm000103`-`nm000107`.
- The recipe name follows S2S's Context rule (`nemar-floor-zarr`, or `nemar-floor` with input `zarr` after Q0 and Q0b); the runbook writes the form the released head documents.

## Decided design

Settled, the runbook's sections:
1. **The bar, item by item**: each with its evidence link (the release tag and its green CI run; S3a and S3b documents; C2, L1, S4 PRs and the runner release; S2D's evidence README; the rollback check output or "not needed under OQ2 A"; the cap) and `met` or `not met`. Any `not met` ends the document there.
2. **Owner step 1, the cap**: under OQ2 A, the merged default PR and the release that carries it; under OQ2 B, the policy file (the current policy plus `"runners": {"maxLiveJobs": {"cpu": 2, "gpu": 0}}`) and `nemar admin compute policy set --file <file> --note "runner cap 2 before the first production runner jobs"`, run only after the rollback rule's output shows two releases with the epic.
3. **Owner step 2, the image**: `bunx cfman wrangler --account sccn secret put COMPUTE_RUNTIME_IMAGE -c backend/wrangler-sccn.toml` with the verified digest reference (the same `cosign verify` as S2S step 1).
4. **Owner step 3, the switch pull request**: the exact diff, for the owner to apply on a branch of the owner's own and open for review: `COMPUTE_ENABLED = "1"` and `COMPUTE_RUNNERS_ENABLED = "1"` in the production `[vars]` table only, never in `[env.dev.vars]`; the matching edit of `backend/test/compute-switches-flag.test.ts` (it allows exactly these two names in the production table and still fails every other table and `COMPUTE_PIPELINES_DISPATCH_ENABLED` anywhere); and the sentence of `AGENTS.md`'s compute switch rule updated to say which switch is on and since which release. Merged into `dev` and released to `main` by the owner.
5. **Owner step 4, the production runner**: registration with the owner's key, `nemar admin compute runners register prod-b --pool cpu --cores <C> --memory-mb <M> --gpus 0 --scratch-gb <S> --backend local --runtime <the runtime of ON> --arch amd64 --site lab_b --trust lab --json` (S2S's formulas, with the shared host's quarter of memory), the secret piped into the runner host's secret file, and the installed signed runner's configuration with `api_base` the production API, `verify_images` true, `slots` 1, and the `availability` object as S2D ran it (`claim_memory_mb` M, the reservation directory); the user units with their priority lines (S4); `doctor` prints `availability` and `priority` yes.
6. **Owner step 5, the first jobs**: five named public datasets chosen by the preparer against DM-02's criteria (listed with their versions and store counts, read from public production endpoints with `env -u TEST_API_URL`), dispatched one at a time with `nemar admin compute pipeline run nemar-floor-zarr --dataset <id>@<version> --executor runner --json`, at most 2 live; after each, `nemar admin compute jobs record <job> --json` shows `finished`, `accounting` `none`, `charged_milli` 0.
7. **Acceptance and stop**: five `finished`, zero `runner_lost`; any `runner_lost`, a ledger row for a runner job, or a refusal not explained by the dataset stops the sequence, and the switch PR's revert is the first recovery (with the policy recovery of ADR 0118 P2 item 7 if a stored key is involved).
8. **The shared machine and the runtime**: the shared-machine rule of the Context in plain words for the people who share the host (what the runner takes, its priority, no preemption, how to pause it, who to ask), the runtime of the owner's ON answer with its residual risk in one sentence, and a pointer to the gated runbook page's etiquette section (W2); a job dispatched while the host is busy waits `created` until it is idle, which is expected, not a stop.
The implementer may choose: the five datasets, and the document's wording.
