## Goal

Every signalJourney document a recipe writes records the nemar-process build that produced it (release `X.Y.Z`, or a dev `X.Y.Z-devN` marked as dev, or a source run marked as source), its commit, and the image's version tag beside its digest, read from inside the image with no network call. The image workflow refuses to publish an image whose version is not the release version of the commit it builds, so the image tag, the git tag `vX.Y.Z` and the recorded version always agree.

## Decided design

Settled (reason in one line each):
- **Recorded fields**, in `extensions.nemar` because `pipelineInfo` is closed to new keys:
  - `process = {"version", "commit", "build"}`, where `build` is `release`, `dev` or `source`;
  - `image = {"digest", "tag"}`;
  - plus what is already there: recipe id and version (also in `pipelineInfo.name` and `pipelineInfo.version`), engine versions, dataset `source_commit`, and for Zarr input DM-13's reader, `index_sha256` and the commit attestation.
  - `engine_info` adds `torch` and `pamica` versions when the distributions are installed (`importlib.metadata`), so an ICA recipe records them without a recipe change.
  The same `process` block goes into the dataset-level document.
- **How a recipe learns its build:** the image carries `/opt/nemar/build.json`, `{"version", "commit", "build"}`, written at image build from three build arguments: `NEMAR_PROCESS_VERSION`, `NEMAR_PROCESS_COMMIT` (replacing the use of `SOURCE_COMMIT`) and `NEMAR_PROCESS_BUILD`. They are mirrored as the labels `org.opencontainers.image.version` and `org.opencontainers.image.revision` and `io.nemar.build`. Package metadata cannot be used, because the project is not an installed distribution.
  - `build.build_info()` reads that file. Outside an image it returns `build: "source"`, the `pyproject.toml` version beside the package, and `commit: null`. It never makes a network call.
- **Dev can never pass as release:**
  - The Dockerfile's argument defaults are `NEMAR_PROCESS_BUILD=dev` and an empty version and commit, and a `RUN` step refuses to build with an empty version or commit, or a `build` outside the three words.
  - `build_info()` refuses a `release` file whose version carries `-dev`, and a `dev` file whose version does not.
  - Only the publish job passes `release`; the pull-request test build passes `dev`.
- **Image workflow change** (the only edit):
  - The `id: version` step also reads `[project].version` from `pyproject.toml` at `GITHUB_SHA` with `tomllib`. It fails unless the tag-derived or dispatched version equals it, the version has no `-dev` suffix, and the git tag `v<version>` exists and points at `GITHUB_SHA` (`git rev-parse "v<version>^{commit}"`).
  - The build steps pass the three build arguments: `NEMAR_PROCESS_BUILD=release` in the publish job and `dev` in the test job.
  - The tag trigger `image-nemar-python-v*`, the `merge-base --is-ancestor` refusal, `SIGNING_IDENTITY` and the job permissions stay unchanged, so signatures stay valid: the identity names the workflow path and the ref, not the file's content.
  - REL-1's byte-identical test stays opt-in. `tests/release/test_workflows.py` adds assertions that those guard lines are present and unchanged, and that the version step contains the pyproject and tag checks.
  - To publish image X.Y.Z when `main` has moved past `vX.Y.Z`, the owner pushes `image-nemar-python-vX.Y.Z` on the `vX.Y.Z` commit; `docs/images.md` says so.
- **Contract test:** for every recipe in the registry, a run on the repository's EEG fixtures checks that the recording and dataset documents carry `extensions.nemar.process.{version,commit,build}`, `image.digest`, recipe id and version, and the engine versions. It also checks that `build` is `source` there, and that the vendored validator accepts both documents.
The implementer may choose: helper names, how `build.json` is written in the Dockerfile.
