## Goal

## Decided design

Settled:
1. **The binary.** In the builder stage of both Dockerfiles, a `RUN` step downloads `https://github.com/sccn/pAMICA/releases/download/v0.4.0/amica15-linux-x64` and refuses to continue unless its SHA-256 is `ada316d3cd8819a5e506b51b48eb464eccba133b81d4efbf63f977e680bb6b1a`; the final stage copies it to `/opt/amica/amica15` (mode 0755, owned by root) and writes that hex digest to `/opt/amica/amica15.sha256`. If `ldd /opt/amica/amica15` in the final image lists anything `not found`, the final stage installs exactly that Debian package at the version `apt-cache policy` shows for the base digest (for example `libgomp1=<version>`), with `--no-install-recommends` and the lists removed.
2. **The CUDA flavor.** `Dockerfile.cuda` repeats the CPU Dockerfile's stages and base digests, syncs `--group runtime --extra cuda`, and sets `io.nemar.flavor="cuda"`; it writes the build file the same way. The `cuda` extra pins torch per QB, sent by `[tool.uv.sources]` to a new explicit index `pytorch-cu128` (the `cu128` directory of the index the `cpu` extra uses); `[tool.uv] conflicts = [[{ extra = "cpu" }, { extra = "cuda" }]]`.
3. **Smoke, both flavors** (`smoke.py`, run by the test build): `ldd /opt/amica/amica15` has no `not found`; the file's SHA-256 equals `/opt/amica/amica15.sha256`; `pamica.AMICANative(binary="/opt/amica/amica15", threads=1, max_iter=5, seed=5489)` fits a 4-channel, 2,000-sample matrix drawn with `numpy.random.default_rng(5489)` and returns a 4 by 4 unmixing matrix; a 5-iteration pAMICA torch fit on CPU in float64 runs. CUDA flavor also: `torch.version.cuda` starts with `12.8`, and `torch.cuda.get_arch_list()` is printed into the smoke output and the digests record; under QB B the smoke fails unless it contains `sm_70`. The CUDA flavor's smoke runs the way a job the runner kept off the GPU runs (`--env NVIDIA_VISIBLE_DEVICES=void`, on the hosted runner): `torch.cuda.is_available()` is false and the 5-iteration CPU float64 fit runs. Both flavors print `CPUFIT sha256=<hex>`, the SHA-256 of that fit's unmixing written with `format(x, ".17g")`, into the smoke output and the digests record: a reading, not a gate (two torch builds may differ in the last bits; card Q1 takes the CPU reference from the CUDA image itself, never from the CPU flavor).
4. **Workflow.** The test build and smoke run for both flavors on every pull request; the publish job (unchanged guards) pushes `<version>-cpu` and `<version>-cuda`, signs each digest with the unchanged identity, and the digests artifact lists both flavors' OCI digests, the CPU SIF as today, and the CUDA flavor's architecture list. The CUDA flavor publishes no SIF in this card (a GPU host builds one from the verified OCI digest, as DM-14 allowed).
5. **`nemar-recipe version`** adds `"flavor"` (read from a one-word file `/opt/nemar/flavor` that each Dockerfile writes as root; `build.json` and its writer stay as PX-10 left them) and `"amica15_sha256"` (read from `/opt/amica/amica15.sha256`); outside an image both are `null`.
The implementer may choose: how the download step is written (Python's standard library or `curl` already in the builder), the free-disk step's contents.
