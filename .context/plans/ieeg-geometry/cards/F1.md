## Goal

Every number a write or refusal rests on is in the P1 report JSON, so a summary never needs `inspect`, and the FreeSurfer track and the subject-surface builder apply the same ECoG minimum.

## Context

- Read `.context/plans/ieeg-geometry/r1-report.md`, its follow-ups section, and `scripts/ieeg_geometry/schema/geometry-report.v1.json`.
- R1 found: the report omits the SPM field check's centroid and extent, the FreeSurfer registration's side fraction, centroid, extent and affine residual, the SPM depth-contact median, and which label rule (1.0 mm on-vertex or 2.0 mm ECoG) applied; and `surfaces_out` uses the ECoG rule only with at least 8 ECoG contacts (`MIN_ECOG_CONTACTS`) while `freesurfer` places cortical contacts from 3 (`MIN_CONTACTS`), so on002799 sub-294 and sub-303 (all ECoG) show `contact_type: seeg` in their surface entries.

## Scope

`scripts/ieeg_geometry/ieeg_geometry/{pipeline,labels,freesurfer,spm,surfaces_out}.py` (adding numbers to decision records only, plus the minimum), `schema/geometry-report.v1.json` (a version bump to 2 if fields change shape; additive optional fields keep version 1), `schema/geometry-index.v1.json` only if the surface entry field is renamed (it is frozen and the website reads it: do not rename; add an optional `fit_rule` field instead and keep `contact_type` meaning the contacts' type), `tools/r1_summary.py` to read the new numbers, tests. Nothing else.

## Decided design

Settled:
- Decision records carry, where they apply: label rule (`on-vertex-1.0mm` or `ecog-2.0mm`) and the shift-control minimum; FreeSurfer registration side fraction, centroid, extent and affine residual; SPM field-check median, p10, centroid and extent, and the depth-contact median against the shell (reported, not judged), and the inversion residual.
- One shared ECoG minimum for "fit cortical contacts with the ECoG rule": 3 contacts, as the FreeSurfer track uses; `surfaces_out` adopts it. A surface entry's `contact_type` is the contacts' actual type; the rule applied goes in a new optional `fit_rule` field in the index entry (additive, the website ignores unknown fields only if its validator allows them: check `src/lib/ieeg-spatial/subject-anatomy.ts` in nemarOrg/website staging; if it rejects unknown fields, do NOT add the field and instead put the rule in the report JSON only, and say so).

The implementer may choose: field names inside decision records (document them in the schema).
