## Goal

`ieeg_geometry.labels` proposes a template label for each electrodes file whose frame is missing, wrong or non-standard, accepts a proposal only when the L1 verifier passes, and produces the files to write, so the about 780 subjects already in fsaverage space get a correct label.

## Context

- The plan's "Lead rulings" section (evidence grades, the sEEG plausibility rule, the c_ras choice, open references, one-hemisphere surfaces) overrides this card wherever they differ; use `Fit`'s evidence grade, never a raw threshold of your own.
- Read the plan, `census.md` (track C rows), the L1 package and its README, and BIDS's coordinate-systems appendix for the valid template labels (pin the list in code with its source URL and date).
- The verified track-C datasets are on006107, on006910, on004551, on006914, on006233, on005545, on005007, on005931 and on004370 (contacts on fsaverage vertices). Use small real excerpts (a few subjects' electrodes, CC0 or the dataset's license, recorded in the fixture README) for tests.

## Scope

`scripts/ieeg_geometry/ieeg_geometry/labels.py`, its tests and fixtures, and the `inspect` command's output for labels; nothing else.

## Decided design

Settled:
- Candidates, in order of evidence: (1) a non-standard but recognizable `iEEGCoordinateSystem` value (`MNI152` without variant, case or spelling variants such as `MNI152NLin6ASym`), mapped to the valid label it names; (2) a template named in `iEEGCoordinateSystemDescription` or the dataset README (`MNI305`, `fsaverage`, `Talairach`, a full `MNI152...` variant); (3) blind trials of `fsaverage` and `MNI152NLin2009cAsym`.
- Acceptance: the L1 `fit` must pass for the candidate's reference surface (`MNI305` and `fsaverage` verify against fsaverage; every `MNI152*` and `IXI549Space` against MNI152NLin2009cAsym). A blind candidate (3) is accepted only when the median distance is at most 1.0 mm against the vendored fsaverage6 (contacts on full-resolution fsaverage vertices measure about 0.7 mm against fsaverage6; on004370 measured 0.68 mm in L1) and the same contacts shifted by 10 mm along each axis all fail the ECoG rule (a control showing the fit is specific).
- An `MNI` named without a variant is never written: it is reported as "MNI variant unknown, needs a human label". `Talairach` is never written by this card.
- A frame declared `ACPC`, `ScanRAS`, or with an `IntendedFor` naming a subject's own T1, is never relabeled.
- Output (as a plan object first, written only by an explicit `write(plan, dataset_dir)`): if the electrodes file has no coordsystem, add `<stem>_coordsystem.json` for it with the accepted label; if it has one that is wrong, leave it untouched and add a `space-<label>` electrodes and coordsystem pair with the values in millimeters. Each written coordsystem has `iEEGCoordinateUnits: "mm"`, `iEEGCoordinateProcessingDescription` starting "Computed by NEMAR" (source file, evidence, median and 90th percentile distance, pipeline version) and the method link `https://docs.nemar.org/data/ieeg-geometry/` in `iEEGCoordinateProcessingReference`. Every written path is recorded through L1's ownership writer.
- A subject that already has a `space-` file for the accepted label gets nothing.

The implementer may choose: the regular expressions for prose (test each), and the plan object's shape.

## Acceptance

- `uv run --project scripts/ieeg_geometry pytest -q` passes with tests that each fail without the code, including: an on006107-style file with no coordsystem gets a `fsaverage` sidecar; an on006910-style "patient-native RAS" coordsystem is left untouched and a `space-fsaverage` pair is added; the same contacts shifted 20 mm are rejected; `MNI` without variant is reported and nothing is written; an `ACPC` file is never relabeled; a second run on its own output writes nothing new and produces byte-identical files.
- `python -m ieeg_geometry inspect` shows the proposal, its evidence and the verdict for a fixture of each kind; quote it in the PR.
