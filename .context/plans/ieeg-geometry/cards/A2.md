## Goal

When a recording's dataset has a NEMAR geometry index with an entry for the recording's electrodes file, the website's Brain panel offers "This subject's anatomy" and draws that subject's own cortical surface under the contacts, in the contacts' own frame, with an honest label.

## Context

- The website is `nemarOrg/website` (Astro, Bun, Biome, vitest; read its AGENTS.md and `.rules/`). The Brain panel is `src/lib/ieeg-spatial/` (`panel.ts` reducer plus shell, `brain-gl.ts`, `mesh-format.ts`, `transforms.ts`, `export.ts`), decided by website ADR 0033; the template surface is loaded by `loadTemplateSurface` from `public/vendor/brain-templates/`.
- The index format is frozen: `scripts/ieeg_geometry/schema/geometry-index.v1.json` in nemar-cli on `origin/epic/ieeg-geometry` (read with `gh api "repos/nemarOrg/nemar-cli/contents/scripts/ieeg_geometry/schema/geometry-index.v1.json?ref=epic/ieeg-geometry" --jq .content | base64 -d`). Meshes are `brain-mesh v1`, content-addressed under `meshes/`, paths relative to the index.
- Where the index lives: `geometry/index.json` beside the dataset's Zarr copy, that is the Zarr index's `data_base` plus `geometry/index.json` (for on004457: `https://nemar.s3.us-east-2.amazonaws.com/on004457/zarr/geometry/index.json`). Use the same base and the same fetch path the viewer already uses for Zarr data; no new host. Nothing is uploaded there yet (card P3 does that), so build against a local fixture served by the dev server or the test harness, and treat a 404 as "no subject anatomy".
- A real index and meshes for testing can be generated from nemar-cli's package: `uv run --project scripts/ieeg_geometry python -m ieeg_geometry.surfaces_out <dataset-dir> --out <dir>` (on004457 sub-2, on004473 sub-1, on003848 sub-RESP0699 work; see that package's network tests for how they assemble a dataset directory). Commit only a small fixture (a decimated mesh under 300 KB per hemisphere is fine for tests).

## Decided design

Settled:
- Website ADR 0034 (write it in this PR, status proposed): subject anatomy from NEMAR's geometry index, in the contacts' own frame, never mixed with template placement; it resolves ADR 0033's open item "whether to draw subject anatomy from FreeSurfer derivatives".
- The Frame row gains the option "This subject's anatomy" when the index has an entry whose `electrodes` path equals the electrodes file the panel is showing (match on the dataset-relative path); it is the default for that file when present, since it is the subject's real brain. The template options are unchanged.
- The entry is validated strictly in code (schema, version, hemisphere keys, mesh SHA-256 of the fetched bytes before decode); any mismatch hides the option and logs one console warning, never a broken drawing.
- Only the hemispheres present are drawn; a one-hemisphere subject says so in the notes ("Right hemisphere only: the dataset ships one hemisphere for this subject").
- Label in the template-label slot: "This subject's anatomy, from the dataset's own surfaces"; for grade `plausible` add "approximate alignment (depth contacts)"; for `specific` nothing more. Notes cite the source surface paths from the entry. Exports (PNG, SVG, views.json) carry the same label.
- Activity coloring, selection, view controls and the 2D views work unchanged on the subject surface; the 2D views' outline uses the subject mesh.
- No network request for the index while the Brain panel is closed; one request per dataset when it opens (cached for the session).

The implementer may choose: module boundaries inside `src/lib/ieeg-spatial/`, how the reducer represents the new frame option, fixture construction.

## Stop conditions

- The viewer has no existing way to reach the Zarr `data_base` from the Brain panel without a new host or a CSP change.
- The index schema lacks a field the panel needs (report it as a patch note for nemar-cli; do not change the schema).
- A mesh fails to decode with the website's decoder.
