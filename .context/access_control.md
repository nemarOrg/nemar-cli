# NEMAR Access Control Implementation

> **Decision recorded:** [ADR 0002 - Access control rides on GitHub collaboration](decisions/0002-access-control-via-github-collaboration.md).
> This document keeps the implementation detail; the ADR is the record of what was decided and why.

## Core Principle: Controlled Access via GitHub Collaboration

Users provide their **GitHub username** during signup. The NEMAR backend:
1. Creates repos using Admin PAT
2. Adds users as GitHub collaborators with appropriate permissions
3. Users interact with repos using their own GitHub accounts

```
User CLI / GitHub UI  →  GitHub (user's own auth)  →  nemarDatasets repos
         ↑                                                    ↑
         │                                         Created by Admin PAT
         │                                         User added as collaborator
         │
NEMAR Backend only for:
  - Repo creation
  - Adding collaborators
  - Generating S3 presigned URLs
  - Dataset ID assignment
```

**Key insight:** For PR merging, users use GitHub's native UI or `gh` CLI with their own credentials. GitHub Actions handle S3 operations.

---

## The Two Key Requirements

### 1. GitHub: Write Access, No Delete
- ALL NEMAR users can push branches to ALL dataset repositories
- Users **cannot** delete repositories
- Users **cannot** push to main (branch protection)
- Only owner/admin can merge PRs
- Solution: Add all users as **collaborators with push permission** on all repos

### 2. S3: Write Access, Version Control for Safety
- Users can upload files to their dataset prefix
- Users **cannot** delete files (or deletion is recoverable)
- Solution: S3 bucket versioning + presigned URLs (no direct credentials)

## Implementation Architecture

### GitHub Strategy

```
nemarDatasets Organization
├── Owner: You (admin account)
│   └── Full control: create, delete, manage
│
├── CLI Backend Service
│   └── Uses admin PAT for:
│       - Creating repositories
│       - Adding/removing collaborators
│       - Managing branch protection
│
└── Individual Users
    └── Collaborator access (push only):
        - Can push commits
        - Can create branches
        - CANNOT delete repository
        - CANNOT change settings
```

**How it works:**
1. User runs `nemar dataset upload`
2. CLI sends request to backend with user's API token
3. Backend validates token, creates repo with admin PAT
4. Backend adds user as collaborator with `push` permission
5. Backend returns repo URL to CLI
6. CLI uses DataLad to push (user has push access via their GitHub account)

**Wait, how does the user push without credentials?**

Option A: User links their GitHub account during signup
- During `nemar auth signup`, user authorizes NEMAR GitHub App
- App grants push access to specific repos only
- User's existing GitHub auth handles the push

Option B: CLI uses backend-provided credentials
- Backend generates short-lived GitHub tokens for specific repos
- CLI uses these tokens for push operations
- Tokens expire after upload completes

**Recommended: Option A** (GitHub App)
- User authenticates their GitHub once
- NEMAR GitHub App installed on user's account
- App has permission to push to nemarDatasets repos where user is collaborator

### S3 Strategy

```
s3://nemar/ (Your bucket, you own it)
├── Bucket Policy: Deny delete except for admin
├── Versioning: Enabled (all versions kept)
│
├── nm000101/
│   └── Files uploaded via presigned URLs
│       - URL generated by backend
│       - Scoped to specific prefix
│       - Expires in 1 hour
│       - PUT only, no DELETE
│
└── nm000102/
    └── Different user's files
```

**How presigned URLs work:**
1. User runs `nemar dataset upload`
2. CLI validates BIDS dataset locally
3. CLI sends file manifest to backend
4. Backend generates presigned PUT URLs for each file
5. CLI uploads files directly to S3 using presigned URLs
6. User never sees AWS credentials

**S3 Bucket Policy (enforce no delete):**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadAccess",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::nemar/*"
    },
    {
      "Sid": "DenyDeleteExceptAdmin",
      "Effect": "Deny",
      "Principal": "*",
      "Action": [
        "s3:DeleteObject",
        "s3:DeleteObjectVersion",
        "s3:DeleteBucket"
      ],
      "Resource": [
        "arn:aws:s3:::nemar",
        "arn:aws:s3:::nemar/*"
      ],
      "Condition": {
        "StringNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::YOUR_ACCOUNT_ID:user/nemar-admin"
        }
      }
    }
  ]
}
```

## User Workflow

### Signup
```
1. nemar auth signup
   - Enter: NEMAR username, email, password
   - Enter: GitHub username (required for collaboration)
   - Verify: Email confirmation
   - Wait: Admin approval

2. Admin approves (nemar admin approve username)
   - Backend generates NEMAR API token
   - User's GitHub username is stored
   - User is now active
   - When user creates dataset: added as GitHub collaborator
```

### Why GitHub Username?
- Users merge PRs via GitHub UI (not through NEMAR backend)
- Users push to branches using their GitHub credentials
- GitHub Actions run with repo secrets (not user credentials)
- NEMAR backend only adds users as collaborators, doesn't manage their GitHub auth

### Upload Dataset
```
1. nemar dataset upload /path/to/bids --name my-dataset

2. CLI validates BIDS locally

3. CLI sends to backend:
   POST /api/datasets/create
   Body: { name: "my-dataset", files: [...] }

4. Backend:
   - Creates GitHub repo: nemarDatasets/nm000XXX
   - Adds user as collaborator (push permission)
   - Generates presigned URLs for all files
   - Returns: { dataset_id, repo_url, upload_urls }

5. CLI uploads files to S3 via presigned URLs

6. CLI creates DataLad dataset and pushes to GitHub
   - User's GitHub auth is used (via GitHub App)
   - Only metadata pushed to GitHub
   - Large files already on S3

7. Done: Dataset available at
   - GitHub: https://github.com/nemarDatasets/nm000XXX
   - S3: s3://nemar/nm000XXX/
```

### What User Cannot Do
```
- Delete GitHub repository (no admin permission)
- Delete S3 files (no delete permission in presigned URLs)
- Access other users' datasets (presigned URLs scoped to their prefix)
- Upload without validation (backend requires valid BIDS)
```

### What Admin Can Do
```
- nemar admin users --pending   # See pending approvals
- nemar admin approve <user>    # Approve user
- nemar admin revoke <user>     # Revoke all access instantly
- nemar admin doi create <id>   # Create concept DOI
```

## Recovery Scenarios

### User "Deletes" S3 File
1. With versioning enabled, delete just creates a "delete marker"
2. Previous version still exists
3. Admin can restore: `aws s3api delete-object --bucket nemar --key nm000XXX/file.edf --version-id DELETE_MARKER_ID`

### User Account Compromised
1. Admin runs: `nemar admin revoke username`
2. Backend immediately:
   - Invalidates API token
   - Removes GitHub collaborator access from all repos
   - Logs incident
3. Data remains intact (user just cannot access)

### User Wants to Delete Their Dataset
1. User contacts admin
2. Admin reviews request
3. Admin manually deletes (with proper authorization)
4. This is intentional friction to prevent accidents

## Tech Stack for Access Control

| Component | Technology | Purpose |
|-----------|------------|---------|
| User Auth | NEMAR API Tokens | Identify users |
| GitHub Access | GitHub App + OAuth | Push to repos |
| S3 Access | Presigned URLs | Time-limited uploads |
| Backend | Cloudflare Workers | Generate tokens/URLs |
| Database | Cloudflare D1 | Store user/dataset mappings |
| Audit | D1 + Logs | Track all operations |
