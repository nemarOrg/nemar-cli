# Python dependencies for the NEMAR Zarr converter driver (generate_zarr.py).
#
# Declaring biosigIO here (instead of only as a `uv pip install` command in the
# workflow) makes it a real entry in GitHub's dependency graph, so this public
# repo shows up under biosigIO's "Used by" / Dependents and the converter work is
# credited to neuromechanist/biosigio. It also single-sources the version pin for
# both the Actions workflow and the Hallu cron.
#
# Extras: [zarr] -> zarr v3 store writer/reader; [meg] -> mne (.fif + BrainVision
# .vhdr + CTF .ds + KIT/Yokogawa + 4D-BTi importers); [mef3] -> mne>=1.12 + pymef
# (MEF3 .mefd iEEG import; kept as its own extra upstream because it pins a newer
# MNE than [meg] alone needs). Core biosigIO covers .set/.fdt/.edf/.bdf.
# >=1.2.0: streams EDF/BDF via pyedflib (importer parity), so generate_zarr.py's
# _biosigio_streams_edf() gate flips on and large EDF converts instead of OOMing
# (nemar-cli#944).
# >=1.2.1: int16 export zero-fills non-finite (NaN/inf) samples and flags the
# channel instead of failing the whole recording -- a NaN in one MISC/aux channel
# (MoBI accelerometer/force/sync) no longer sinks a dataset's EEG coverage
# (biosigio#107). Bumping the pin forces the idempotent cron install to upgrade.
# >=1.2.2: EEGLAB importer loads column-form (N, 1) chanlocs/event struct arrays
# instead of silently truncating the recording to one channel (biosigio#110,
# root cause of nemarDatasets/on002718#1); pairs with this repo's
# channel_count_mismatch fidelity gate.
# >=1.2.3: adds MEF3 .mefd import (mne.io.read_raw_mef + pymef, [mef3] extra) and
# 4D/BTi import (mne.io.read_raw_bti, content-detected -- no extension), both with
# bounded-memory streaming support. This is the release generate_zarr.py's
# .mefd/BTi discovery (dir_recording_of/bti_recordings) depends on; the [mef3]
# extra must be added here too, or .mefd recordings raise ImportError at convert
# time even though discovery finds them. nemarOrg/nemar-cli#1095 (track: #1097).
# >=1.2.4: two classes of recording that were being discarded despite being fully
# readable now convert.
#   - MATLAB v7.3 (HDF5) EEGLAB `.set` (biosigio#114, closing biosigio#21).
#     MNE refuses these outright and scipy.io.loadmat cannot read them either,
#     since a v7.3 `.set` is an HDF5 container, not a classic MAT file. Read via
#     h5py, which is the `[hdf5]` extra -- added below for exactly the same reason
#     `[mef3]` was: without it these raise ImportError at convert time even though
#     discovery finds them. 544 recordings measured across the archive.
#   - Three false EDF/BDF rejections (biosigio#116, closing biosigio#109):
#     a channel with physical_min == physical_max (legal EDF -- a referential
#     montage's reference electrode is identically zero by construction, and one
#     such channel was discarding the whole recording), a numeric header field
#     NUL-padded instead of space-padded, and discontinuous EDF+D. Recovered reads
#     are numerically identical to a pyedflib read (verified at machine-epsilon on
#     real recordings, all channels) and are flagged via `edf_tolerant_read`.
#     Genuine truncation is still reported as corruption. ~4,332 recordings across
#     23 datasets, the largest single cluster.
# >=1.2.5: reads CTF `.ds` recordings whose `.hc` names the head coils
#   `Nasion`/`LPA`/`RPA` (biosigio#117). MNE substring-matches that descriptor
#   against a case-sensitive `nasion`/`left ear`/`right ear` table, so every coil
#   parsed as unknown and the whole recording failed with "Some of the mandatory
#   HPI device-coordinate info was not there" -- the coil coordinates were
#   present and correct the entire time. 380 recordings in on006502, which is
#   every recording it has (nemarOrg/nemar-cli#1125). Fixed upstream too
#   (mne-tools/mne-python#14191, merged), but no MNE release carries it yet;
#   biosigIO's shim is gated on that and no-ops once one does.
# >=1.2.6: three things index format v3 reads or depends on (epic #1181 phase 7).
#   - View levels are chunked at a CONSTANT 1024 COLUMNS instead of a constant
#     ~4 s, and the geometry is declared in attrs instead of having to be probed
#     (biosigio#126, this repo's #1178 items 1-2). A viewport needs ~1000-2500
#     columns at ANY level, so constant-seconds chunking made a zoomed-out read
#     594 requests for 1.16 MB on a 40-minute store; constant-columns makes it 3.
#     The attrs are what index v3 republishes per group: group `n_view_levels` /
#     `view_levels` / `view_downsample` / `view_chunk_columns` / `chunk_seconds` /
#     `shard_seconds`, level-0 `source_rate_hz` / `chunk_samples` / `shard_samples`,
#     view-array `chunk_columns`, root `view_chunk_columns`.
#   - Adopting a channels.tsv `units` value CONVERTS the channel's samples into
#     that unit rather than only relabeling them, exempts the discrete channel
#     types, and reports what it did per file in
#     `rec.metadata["channels_tsv_units"]` (biosigio#125, closing #122), which
#     the converter republishes as the index's per-store `units_report` -- so a
#     unit that could NOT be adopted is visible on the public surface instead of
#     being silently served.
#   - Resource exhaustion propagates as `MemoryError` (and friends) instead of
#     being reclassified as a data failure (biosigio#124), which is what keeps
#     `convert_one`'s `except MemoryError` handler -- and therefore the retryable
#     `recording_memory_exceeded` code -- reachable for reader-side exhaustion.
# >=1.2.7: `stream_to_zarr` takes `bids_channels` too, with the same values as
# `Recording.from_file` ("auto" / "off" / None / a path / a DataFrame), and the
# trailing-slash sidecar lookup is fixed on both paths (biosigio#128, closing
# #127). THIS IS A FLOOR, not a preference, and it is what lets the engine go to
# "3":
#   - Without it the two exporters disagree about units. 1.2.6's streaming
#     exporter had no such parameter at all, so a dataset's small recordings
#     carried the sidecar's units and its large ones carried the importer's --
#     re-converting the archive under a half-applied rule would have baked that
#     split into the serving copy, which is why phase 7 shipped with the engine
#     still at "2".
#   - 1.2.6's `Recording.from_file` ACCEPTS `bids_channels=<path>` and silently
#     treats anything that is not "auto" as "off" (measured: the units report
#     comes back None). So a driver that passes the path form on 1.2.6 believes
#     the sidecar was applied and serves importer units. There is no capability
#     probe that saves you from that; only the floor does.
# The converter passes the sidecar EXPLICITLY on both paths (`bids_channels_arg`)
# and never uses "auto": the file handed to an exporter is a scratch
# materialization, and on the ADR 0028 MaxShield path it is the filtered copy at
# `work/sss_<basename>`, so sibling detection is the wrong question -- and BIDS
# inheritance means the applicable sidecar may live in an ancestor directory
# rather than beside the recording at all.
# >=1.2.8: the streaming export writes each level-0 shard and view chunk once,
# in aligned blocks, instead of rewriting every shard once per channel
# (biosigio#129/#130, nemar-cli#1483). Same bytes out; on a 128-channel EDF,
# 110 s -> 8.8 s and +5.1 GB -> +1.8 GB RSS. The rewrites held whole shards in
# flight per channel, which is what tripped the per-worker RLIMIT_DATA budget
# as `recording_memory_exceeded` on on004789. Output is identical, so the engine
# stamp does not move.
# >=1.2.9: converts real files that failed before. EEGLAB v7.3 `.set` with the
# struct flat at the HDF5 root, or with empty `chanlocs`/`event` fields
# (biosigio#131); BrainVision headers whose `DataFile=`/`MarkerFile=` still name
# pre-BIDS-rename files (biosigio#132); repeated EDF/BDF/WFDB channel labels,
# which used to overwrite each other and are now suffixed as MNE does
# (biosigio#133; EEGLAB keeps its own `_2`, `_3` scheme). We observed these as
# datasets left on an old (v1) Zarr, and the repeated-label EDF case as a
# `channel_count_mismatch` refusal (nm000110); biosigio's changelog makes
# neither claim. Host I/O errors (EACCES, EIO, ENOSPC, ...) are now raised as the
# OSError itself, which the converter records as an uncoded infrastructure
# failure and retries, instead of a typed file failure (biosigio#139). No
# nemar-cli caller uses `add_channel`, which now raises on a duplicate label.
# ZARR_ENGINE_VERSION is deliberately NOT bumped (ADR 0033): this is a bug fix,
# not something the engine "can now see", and a bump would requeue the whole
# archive. Stores that already converted are unchanged; the stranded datasets are
# recovered by a targeted `--dataset` or requeue run, not by the stamp. A
# recording that repeats an EDF label gets suffixed channel names when it is
# reconverted, and `recording_metadata` gains `channel_labels_deduplicated`,
# `brainvision_header_recovered` and `eeglab_fdt_recovered`, each only when it
# applies.
# >=1.2.10: a channels.tsv row that matches no channel exactly is applied to
# the one channel whose label differs from it only in case (biosigio#140,
# closing #136; CHB-MIT's `Fp1-F7` against the EDF header's `FP1-F7`), when
# that is unambiguous. Its type and unit are now APPLIED, so a unit that
# differs from the file's CONVERTS the samples: a store regenerated from such a
# dataset (nm000110) can differ in channel types, units and values from the
# one published before. biosigIO lists each such match in its own report as
# `matched_case_insensitive`, `{sidecar_name: channel_label}`; the converter
# republishes that bounded, as `units_report.matched_case_only` (a count) and
# `matched_case_only_examples` (at most CASE_MATCH_EXAMPLES_MAX), never as the
# per-channel map, and the schema refuses the map. `unmatched_case_only` stays
# declared for stores converted before 1.2.10 and for ambiguous rows. The
# schema, zod and MCP texts for the join were reworded with this bump, and the
# canary `test_a_case_only_row_is_applied_and_reported_per_biosigios_join` now
# runs against this pin in CI. Also in 1.2.10: the XDF, EEGLAB, neo and Trigno
# importers record `channel_labels_deduplicated` too, and their repeat suffixes
# never take a label the file really uses (so `Fz, Fz, Fz_2` is `Fz, Fz_3,
# Fz_2`, where 1.2.9 gave the second `Fz` the label `Fz_2`); Trigno keeps
# repeated columns; `select_channels` raises on a repeated name; EDF export
# numbers labels that collide once truncated. No nemar-cli code calls
# `select_channels`, `add_channel` or the EDF exporter.
# ZARR_ENGINE_VERSION is again NOT bumped (ADR 0033): the stamp records a
# widening of discovery, and 1.2.10 discovers exactly what 1.2.9 did. Stores
# already published stay served until their dataset is requeued (ADR 0005).
# 1.2.10 changes a store's bytes only for a sidecar that differs from the file
# only in case, or for an XDF/EEGLAB/neo/Trigno file whose repeats collide with
# a label it really uses. Stores converted since the join report was added
# (0.10.9) show the first as `unmatched_case_only`, and
# `find_collapsed_channel_stores.py --case-only` lists them from the published
# index.json (read-only); it also counts, as unverifiable, the entries with no
# join report, which the index cannot answer for (older stores: compare their
# channels.tsv with the store's labels). The XDF/EEGLAB/neo/Trigno collision
# has no detector. Either way the fix is a targeted `--dataset` or requeue
# run, one dataset at a time, not the stamp.
# >=1.2.11: a store carries no subject information (#1626). biosigIO's three
# store writers (`Recording.to_zarr`, `ZarrExporter.export`, `stream_to_zarr`)
# take `exclude_subject_info`, which removes the members
# `biosigio.SUBJECT_INFO_KEYS` names (patient code and name, sex, birth date,
# age, the EDF operator and administrative fields, EEGLAB subject and group,
# WFDB comments, and the read-recovery provenance `brainvision_header_recovered`
# and `eeglab_fdt_recovered`) from `recording_metadata` at any depth, reduces
# `source_file` and `bti_pdf_file` to their final path component, and marks the
# store root `subject_info_excluded: true`. The converter passes it on EVERY
# write (`generate_zarr.write_store`) and refuses to convert on a biosigIO that
# lacks it (`biosigio_subject_info_problems`, exit 78), so this is a FLOOR the
# converter enforces itself, not only a pin. Its technical members stay:
# `channels_tsv_units` and `channel_labels_deduplicated`, which the converter
# reads back, are label-keyed maps biosigIO never descends into, and
# `source_file` is still rewritten to the BIDS path afterwards. No converter,
# index or backend code reads a removed member. The default (option off) writes
# exactly what 1.2.10 wrote, so nothing else in a store changes.
# ZARR_ENGINE_VERSION is NOT bumped (ADR 0033): the stamp records a widening of
# discovery, and 1.2.11 discovers exactly what 1.2.10 did. Stores already
# published keep their subject members until they are reconverted or stripped
# in place by a fleet tool that #1626 lists and this release does not build (the scrub's
# `zarr` stage strips one dataset at a time), not by the stamp.
# <1.2.12 is a CAP, not a floor, raised deliberately per release: a biosigIO
# patch release has changed what a store contains three times in a row (1.2.9,
# 1.2.10, 1.2.11), so the next one is read before the converter takes it. Raise
# it in three places at once: here, `BIOSIGIO_SPEC`, `BIOSIGIO_FLOOR` and
# `BIOSIGIO_CAP` in hallu-zarr.sh (setup() refuses an installed biosigIO outside
# [floor, cap) after install, and any pre-release), and test_hallu_zarr_config.py.
biosigio[zarr,meg,mef3,hdf5]>=1.2.11,<1.2.12

# Draft 2020-12 validator for the converter's own pre-upload self-check: the index
# it is about to publish is validated against `shared/zarr-index.schema.json` (and
# the manifest against `shared/zarr-manifest.schema.json`) before either reaches
# S3, so a producer bug surfaces here rather than in every consumer. The check
# degrades to a loud warning when this is absent, so an older venv still converts.
jsonschema>=4.21

# Writes `<id>/zarr/events.parquet` (#1060): one columnar file per dataset, one
# row per (event, channel group), with the level-0 sample index the converter
# computes. Rows are staged per store and appended through a ParquetWriter, so
# this is used for a streaming write, never to hold a 25k-store dataset in one
# frame. biosigIO already pulls in numpy/pandas; pyarrow is the parquet writer
# neither of them brings.
# Like jsonschema, absence is survivable rather than fatal: the converter warns,
# publishes no events file, and leaves index.json advertising none -- so a node
# still running the fallback `BIOSIGIO_SPEC` install (no requirements.txt in its
# clone) converts recordings as before.
pyarrow>=15.0
